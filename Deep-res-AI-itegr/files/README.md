# Веб-чат для доступа к AI-моделям на FastAPI

Исследование архитектурных решений и рабочий пример кода.

---

## 1. Постановка задачи

Веб-чат к LLM должен решать четыре задачи одновременно:

1. **Доставлять ответ по мере генерации** (стриминг), а не одним куском через 10–20 секунд — иначе интерфейс ощущается «мёртвым».
2. **Хранить контекст диалога** между сообщениями пользователя.
3. **Не течь деньгами и секретами** — ключ API никогда не должен попадать на клиент, а размер контекста нужно контролировать.
4. **Масштабироваться** — держать много одновременных соединений, не блокируя event loop.

FastAPI хорошо подходит для этого, потому что:
- построен на ASGI и `async/await` — можно ждать ответ от LLM, не блокируя другие запросы;
- нативно поддерживает и `WebSocket`, и `StreamingResponse` (SSE);
- даёт бесплатную валидацию через Pydantic и автогенерацию OpenAPI-документации;
- легко комбинируется с `httpx`/официальными SDK провайдеров (Anthropic, OpenAI и др.), которые сами асинхронные.

## 2. Выбор транспорта: WebSocket vs SSE vs обычный REST

| Критерий | REST (без стрима) | SSE (Server-Sent Events) | WebSocket |
|---|---|---|---|
| Направление | запрос → один ответ | сервер → клиент (поток) | двустороннее |
| Ощущение "печатающегося" ответа | нет | да | да |
| Проходит через прокси/CDN "из коробки" | да | обычно да | иногда требует настройки (upgrade-заголовки, sticky sessions) |
| Сложность клиентского кода | минимальная | простая (`EventSource` или `fetch` + `ReadableStream`) | чуть выше (управление соединением, реконнект) |
| Подходит для | быстрых операций, фонового API | одностороннего стрима ответа модели | полноценного чата, где нужна отмена генерации, «печатает…», несколько сообщений подряд |
| Автопереподключение из коробки | – | да (у `EventSource`) | нет, нужно писать самому |

**Рекомендация:**
- Если чат — это просто «отправил вопрос → получил стримящийся ответ», **SSE проще и достаточно**: меньше кода, лучше проходит через существующую инфраструктуру (nginx, CDN), тривиально дебажится через `curl -N`.
- Если нужен полноценный чат-опыт (пользователь может прервать генерацию, сервер может проактивно что-то прислать, несколько вкладок на одну сессию и т.п.) — берите **WebSocket**.

В прилагаемом примере кода реализованы **оба варианта** на одном FastAPI-приложении, чтобы можно было сравнить и выбрать нужный.

## 3. Архитектура примера

```
Browser (index.html)
   │  WebSocket  ws://.../ws/chat/{session_id}
   │  или POST   /api/chat/stream  (SSE)
   ▼
FastAPI app (main.py)
   │  хранит историю в SESSIONS[session_id]
   │  вызывает Anthropic SDK в режиме streaming
   ▼
Anthropic API (client.messages.stream)
```

```
ai-web-chat/
├── main.py            # FastAPI-приложение: WS + SSE эндпоинты
├── static/index.html  # минимальный фронтенд на чистом JS
├── requirements.txt
├── .env.example
└── Dockerfile
```

### 3.1. Ядро — потоковый вызов модели

Ключевая часть, вокруг которой всё строится — асинхронный стрим из SDK:

```python
async with client.messages.stream(
    model=MODEL_NAME,
    max_tokens=1024,
    messages=history,
) as stream:
    async for text_chunk in stream.text_stream:
        # text_chunk — очередной кусочек текста ответа
        ...
```

`stream.text_stream` отдаёт уже собранные текстовые дельты (без ручного парсинга SSE-событий самого провайдера) — этого блока достаточно, чтобы подключить любой транспорт поверх (WebSocket, SSE, очередь и т.д.).

### 3.2. WebSocket-эндпоинт

```python
@app.websocket("/ws/chat/{session_id}")
async def ws_chat(websocket: WebSocket, session_id: str) -> None:
    await websocket.accept()
    history = get_history(session_id)
    try:
        while True:
            user_message = await websocket.receive_text()
            history.append({"role": "user", "content": user_message})
            assistant_text = ""
            async with client.messages.stream(
                model=MODEL_NAME, max_tokens=1024, messages=history,
            ) as stream:
                async for chunk in stream.text_stream:
                    assistant_text += chunk
                    await websocket.send_json({"type": "chunk", "content": chunk})
            await websocket.send_json({"type": "done"})
            history.append({"role": "assistant", "content": assistant_text})
    except WebSocketDisconnect:
        pass
```

Важные детали (уже учтены в `main.py`):
- при ошибке модели откатываем последнее сообщение пользователя из истории, иначе следующий запрос уйдёт с «оборванным» диалогом;
- `session_id` генерируется на клиенте (`crypto.randomUUID()`) и передаётся в URL — этого достаточно для демо, но **не для продакшн-аутентификации** (см. раздел 5).

### 3.3. SSE-эндпоинт

```python
@app.post("/api/chat/stream")
async def chat_stream(payload: ChatRequest) -> StreamingResponse:
    async def event_generator():
        async with client.messages.stream(...) as stream:
            async for chunk in stream.text_stream:
                yield f"data: {json.dumps({'content': chunk})}\n\n"
        yield "event: done\ndata: {}\n\n"

    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

Проверяется одной командой:
```bash
curl -N -X POST http://localhost:8000/api/chat/stream \
  -H "Content-Type: application/json" \
  -d '{"session_id": "test", "message": "Привет!"}'
```

## 4. Хранение состояния диалога

В примере история хранится в обычном Python-словаре `SESSIONS` в памяти процесса. Это **работает только для одного воркера на одной машине** и обнуляется при рестарте. Варианты для продакшена:

| Подход | Когда использовать |
|---|---|
| In-memory dict (как в примере) | прототип, демо, один воркер |
| Redis (`redis.asyncio`) | несколько воркеров/подов, нужен TTL для старых сессий |
| PostgreSQL/SQLite + SQLAlchemy | нужна аналитика, история чатов «навсегда», привязка к пользователю |
| Клиент сам хранит историю и присылает её целиком в каждом запросе | самая простая масштабируемая схема без сервера состояния (stateless backend) — подходит, если не боитесь гонять историю туда-обратно |

Дополнительно стоит ограничивать историю (в примере — `MAX_HISTORY_MESSAGES`) или делать суммаризацию старых сообщений, чтобы не упереться в лимит контекста и не платить за токены, которые модель уже не использует осмысленно.

## 5. Безопасность и контроль стоимости

Пункты, обязательные перед реальным продакшеном (в демо-примере упрощены или опущены):

1. **Ключ API только на сервере.** Никогда не передавайте `ANTHROPIC_API_KEY` на фронтенд — весь вызов модели должен идти через ваш backend.
2. **Аутентификация пользователей.** `session_id` из примера — не защита; в реальном приложении привязывайте сессию к аутентифицированному пользователю (JWT в `Authorization`-заголовке или cookie, OAuth2 через `fastapi.security`).
3. **Rate limiting.** Ограничивайте частоту запросов на пользователя/IP, например через `slowapi` (обёртка над `limits`) или на уровне API-шлюза (nginx, API Gateway облака).
4. **Ограничение `max_tokens` и длины истории** — иначе один недобросовестный пользователь может сгенерировать заметный счёт.
5. **Валидация ввода.** Даже простой `Pydantic`-модели (как `ChatRequest`) достаточно, чтобы отсечь заведомо некорректные запросы; отдельно стоит подумать о модерации содержимого при публичном доступе.
6. **CORS.** В примере стоит `allow_origins=["*"]` для удобства разработки — в проде указывайте конкретный домен фронтенда.
7. **Таймауты и отмена генерации.** Дайте пользователю возможность прервать стриминг (на WebSocket — просто перестать слушать и закрыть соединение; на сервере стоит проверять `websocket.client_state`).

## 6. Масштабирование

- **Несколько воркеров Uvicorn/Gunicorn.** Как только воркеров больше одного, in-memory `SESSIONS` перестаёт быть общим — нужен Redis или БД.
- **WebSocket и балансировщик.** Для WS обычно нужны *sticky sessions* (одна и та же клиентская сессия должна попадать на тот же инстанс) либо вынос состояния во внешнее хранилище, чтобы любой инстанс мог его прочитать.
- **Долгие генерации / тяжёлые пайплайны (RAG, агенты с инструментами).** Стоит выносить в фоновые задачи (Celery, ARQ, Taskiq) и присылать результат через WebSocket/уведомление, а не держать HTTP-запрос открытым произвольно долго.
- **Несколько провайдеров моделей.** Оборачивайте вызов модели в свой интерфейс (`async def generate(history) -> AsyncIterator[str]`), чтобы можно было подменить Anthropic на OpenAI/другую модель без изменения эндпоинтов чата.

## 7. Запуск примера

```bash
# 1. Установить зависимости
pip install -r requirements.txt

# 2. Задать ключ API
```

## 8. Возможные развития проекта

- **Function calling / tools** — дать модели доступ к вашим внутренним функциям (поиск в базе, вызов API) через механизм tool use в SDK.
- **RAG (Retrieval-Augmented Generation)** — перед вызовом модели подмешивать в контекст релевантные фрагменты из векторной БД (pgvector, Qdrant, Chroma).
- **Мультимодальность** — приём изображений/файлов от пользователя (SDK уже поддерживает `image`/`document` в сообщениях).
- **Персистентная история и аккаунты** — таблица `conversations`/`messages` в PostgreSQL, привязка к пользователю.
- **Наблюдаемость** — логирование токенов/стоимости на запрос, трейсинг (например, через OpenTelemetry), метрики в Prometheus.
- **Тестирование** — `pytest` + `httpx.AsyncClient` для REST/SSE-эндпоинтов, `websockets`-клиент или `starlette.testclient.TestClient` для WebSocket-эндпоинта, с мокированием ответа `client.messages.stream`.

## 9. Итоговые рекомендации

- Для простого чата с ответом модели — **начинайте с SSE**: меньше кода, проще эксплуатация.
- Переходите на **WebSocket**, если нужна отмена генерации на лету, серверные push-уведомления или несколько параллельных потоков сообщений в одной сессии.
- С первого дня закладывайте **вынос состояния во внешнее хранилище** (даже если сейчас у вас один воркер) — миграция с in-memory на Redis посреди роста нагрузки болезненнее, чем сделать это сразу.
- Разделяйте **транспортный слой** (WebSocket/SSE-эндпоинты) и **слой вызова модели** — это даёт возможность безболезненно добавлять новых провайдеров, RAG, инструменты и тесты.
