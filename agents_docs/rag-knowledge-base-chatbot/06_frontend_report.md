## Часть 1. Образовательный блок: как вообще работает веб-фронтенд

### 1.1. Клиент-серверная модель: где «живёт» фронтенд

Любое веб-приложение — это обмен сообщениями между двумя сторонами:

```
Браузер (клиент)  ── HTTP-запрос (GET/POST/...) ──>  Сервер
Браузер (клиент)  <── HTTP-ответ (HTML / JSON / ...) ──  Сервер
```

- **Браузер** — программа, которая умеет получать и показывать страницы. Браузер понимает три «языка»: **HTML** (структура страницы), **CSS** (внешний вид) и **JavaScript** (поведение: клики, запросы, анимации).
- **Сервер** — программа на чужом компьютере (или в облаке), которая обрабатывает запросы. В этом проекте сервер — это **FastAPI** на Python.
- **HTTP** — протокол общения. Запросы бывают `GET` (получить данные), `POST` (создать/отправить), `PUT`/`PATCH` (обновить), `DELETE` (удалить) и др.

Весь «фронтенд» — это ровно то, что выполняется в браузере: HTML-разметка, стили и JavaScript. Вопрос только в том, **кто и когда эти файлы готовит** — отсюда и разница между подходами ниже.

### 1.2. Два принципиально разных подхода: MPA/SSR и SPA

#### Классический подход (MPA + серверные шаблоны)

Раньше (и до сих пор во многих проектах) сервер сам собирал HTML-страницу и отдавал её готовой. Браузер просто показывал то, что прислал сервер. При каждом переходе по ссылке браузер заново запрашивает новую страницу у сервера.

Инструменты, которые помогают серверу собирать HTML из шаблонов:

- **Jinja2** — шаблонизатор для **Python** (используется в FastAPI/Flask/Django). Шаблон — это HTML-файл со вставками вида `{{ переменная }}` и циклами `{% for ... %}`. Сервер подставляет данные в шаблон и отдаёт готовый HTML.
  ```html
  <!-- шаблон Jinja2 -->
  <h1>Привет, {{ user.name }}!</h1>
  {% for item in items %}
    <li>{{ item }}</li>
  {% endfor %}
  ```
- **Django Templates**, **Jinja2**, **Blade (PHP/Laravel)**, **Thymeleaf (Java)** — аналогичные механизмы в других языках.

Этот подход называют **MPA (Multi-Page Application)** — многостраничное приложение: каждая страница — отдельный HTML-документ с сервера. Плюс — простота и хорошая SEO-индексация. Минус — каждое действие требует перезагрузки страницы, интерфейс ощущается менее «живым».

#### Современный подход (SPA + JavaScript-фреймворк)

**SPA (Single-Page Application)** — одностраничное приложение. Сервер отдаёт **один-единственный** HTML-файл (пустую «оболочку») + большой JavaScript-бандл. Дальше JavaScript сам рисует весь интерфейс в браузере, а с сервером общается только через API-запросы (обычно JSON). При переходе между «страницами» браузер НЕ перезагружается — JavaScript перерисовывает содержимое, подменяя данные.

Именно так устроен фронтенд этого проекта: сервер (FastAPI) отдаёт только JSON по API, а всю отрисовку делает React.

### 1.3. Что такое React

**React** — самая популярная JavaScript-библиотека для построения интерфейсов (создана в Facebook/Meta в 2013 году). Ключевые идеи:

1. **Компоненты** — интерфейс разбивается на переиспользуемые куски-функции. Каждый компонент принимает входные данные (**props**) и возвращает описание того, что должно быть на экране:
   ```tsx
   function MessageBubble({ text, isUser }) {
     return <div className={isUser ? 'user' : 'bot'}>{text}</div>
   }
   ```

2. **JSX/TSX** — синтаксис, в котором HTML-разметка пишется прямо внутри JavaScript/TypeScript-кода. Браузер такого не понимает, поэтому JSX обязательно «транспилируется» (преобразуется) в обычный JavaScript на этапе сборки.

3. **Декларативность + виртуальный DOM** — разработчик описывает, *каким должен быть интерфейс при данном состоянии*, а не *как его менять*. Когда состояние меняется (`useState`), React пересчитывает компонент, сравнивает новое описание со старым (через виртуальный DOM — лёгкую копию реального дерева) и точечно обновляет только изменившиеся части настоящего DOM. Это и есть «реактивность»: интерфейс всегда отражает состояние данных.

4. **Hooks** — функции, дающие компонентам «суперспособности»:
   - `useState` — локальное состояние (переменная, при изменении которой компонент перерисовывается);
   - `useEffect` — побочные эффекты (загрузка данных с сервера, подписки) — выполняется после отрисовки;
   - `useRef` — ссылка на DOM-элемент или изменяемое значение без перерисовки;
   - `useContext` — доступ к «глобальному» состоянию без передачи через props;
   - `useCallback` / `useMemo` — мемоизация (кэширование) функций и значений.

5. **React-экосистема** — React сам по себе решает только задачу отрисовки. Всё остальное — сторонние библиотеки:
   - **react-router-dom** — роутинг («страницы» в SPA);
   - **axios / fetch** — HTTP-запросы к API;
   - **zustand / redux / context** — глобальное состояние;
   - **tailwind / styled-components** — стилизация.

### 1.4. Что такое Vite

**Vite** (от фр. «vite» — быстро) — это **сборщик (bundler) и dev-сервер** для фронтенда, наследник идеологии Webpack, но гораздо быстрее. Зачем он нужен?

Браузер не умеет «из коробки» выполнять TypeScript, JSX, импортировать CSS из `node_modules` и т.д. Нужен инструмент, который:

1. **В режиме разработки (`vite` / `npm run dev`)**:
   - запускает локальный dev-сервер (в этом проекте — на порту `5173`);
   - **транспилирует** TS/JSX на лету (через esbuild);
   - предоставляет **HMR (Hot Module Replacement)** — при сохранении файла изменённый модуль мгновенно подставляется в работающее приложение **без перезагрузки страницы**. В `vite.config.ts` для Docker включён `usePolling` — файловый watch через опрос, т.к. на Windows-томах обычный watch не срабатывает;
   - **проксирует** запросы к бэкенду (см. ниже).

2. **В режиме продакшена (`vite build`)**:
   - собирает всё в статические файлы (`dist/`): минифицированный JS, оптимизированные CSS, хэшированные имена файлов для кэширования;
   - выполняет **tree-shaking** — выбрасывает неиспользуемый код;
   - на выходе — пачка статики, которую можно отдать любым веб-сервером (в проекте — nginx).

Схема:

```
Исходники (TSX/TS/CSS) ── Vite build ──> dist/ (HTML + JS + CSS) ──> nginx ──> браузер
```

### 1.5. Что такое Vue (и чем он отличается от React)

**Vue** — ещё один популярный JS-фреймворк (создан Эваном Ю в 2014 году). По философии он близок к React, но с иным синтаксисом:

```vue
<!-- Vue SFC (Single File Component): шаблон + скрипт + стили в одном файле -->
<template>
  <button @click="count++">Нажато {{ count }} раз</button>
</template>

<script setup>
import { ref } from 'vue'
const count = ref(0)
</script>
```

| | React | Vue |
|---|---|---|
| Синтаксис | JSX (HTML внутри JS) | SFC: `<template>` + `<script>` + `<style>` |
| Реактивность | Явная: `useState` + перерисовка | Магическая: `ref`/`reactive` — данные сами отслеживаются |
| Кто делает | Библиотека + экосистема (роутер, стейт — сторонние) | «Батарейки включены» (официальный роутер, Pinia, DevTools) |
| Кривая входа | Круче из-за JSX и экосистемы | Мягче, шаблоны ближе к HTML |
| Производительность | Сопоставимы, оба используют виртуальный DOM | Сопоставима |

**Вывод**: React и Vue решают одну и ту же задачу (реактивный UI в браузере), просто разными синтаксисами. В этом проекте используется React — Vue здесь не задействован, но упомянут для контекста, чтобы было понятно, что React — не единственный вариант.

### 1.6. Что такое Jinja2 (и почему это «другой мир»)

**Jinja2** — шаблонизатор на Python. Он работает **на сервере**: берёт HTML-шаблон + данные и на выходе даёт готовый HTML. Отношения «сервер-браузер» при этом как в классическом MPA.

```python
# Пример: FastAPI + Jinja2
@app.get("/")
def index(request: Request):
    return templates.TemplateResponse("index.html", {"request": request, "user": "admin"})
```

Сравнение подходов одним взглядом:

| Аспект | MPA + Jinja2 | SPA + React/Vue |
|---|---|---|
| Где рендерится HTML | На сервере | В браузере (JavaScript) |
| Что отдаёт сервер | Готовые HTML-страницы | JSON-данные по API |
| Переход между страницами | Полная перезагрузка | Мгновенная перерисовка |
| Язык серверной логики | Python (или PHP, Java...) | JavaScript/TypeScript |
| SEO | Отличная (HTML виден сразу) | Сложнее (нужен SSR/пререндер) |
| Живость интерфейса | Ниже | Высокая (чат, дашборды) |
| Сложность | Ниже | Выше (сборка, бандлы, состояние) |

**Гибриды**: многие проекты сочетают оба подхода — «обычные» страницы на Jinja2, а сложные интерактивные части (админка, чат) — на React/Vue. В этом проекте всё наоборот по структуре: API-сервер (FastAPI) вообще не рендерит HTML — весь UI отдан SPA на React.

### 1.7. Что такое TypeScript и Tailwind (спутники React в этом проекте)

- **TypeScript (TS)** — надстройка над JavaScript, добавляющая типы. `tsc` проверяет код на этапе сборки (`npm run build` = `tsc && vite build`), что ловит массу ошибок до запуска. Всё содержимое `frontend/src` — `.tsx` (TS + JSX).
- **Tailwind CSS** — CSS-фреймворк «utility-first»: стили пишутся прямо в разметке готовыми классами (`px-4 py-2 rounded-xl text-sm`). Версия 4 подключается как Vite-плагин (`@tailwindcss/vite`), а дизайн-токены (цвета, радиусы, шрифты) задаются в CSS через `@theme` — в этом проекте так настроена тёмная тема «glass» (см. `index.css`).

## Часть 2. Разбор фронтенда этого проекта

### 2.1. Общая архитектура

Фронтенд — это **SPA-админ-панель** («Admin Console» для оператора/администратора Support AI), написанная на:

- **React 19** — отрисовка UI;
- **Vite 7** — сборка и dev-сервер;
- **TypeScript ~5.9** — типизация;
- **Tailwind CSS 4** — стилизация (тёмная «glassmorphism»-тема);
- **axios** — HTTP-клиент для API;
- **react-router-dom 7** — роутинг;
- **lucide-react** — иконки.

Важно: этот фронтенд — только **админка**. Публичный чат-виджет (который общается с клиентами) находится вне этого репозитория — здесь он только эмулируется: страница ConversationDetail позволяет писать сообщения и смотреть, как бот отвечает.

### 2.2. Жизненный цикл: от запроса страницы до интерфейса

```
Браузер запрашивает https://host/
        │
        ▼
nginx: try_files $uri $uri/ /index.html   ← отдаёт ОДИН и тот же index.html для любого пути
        │
        ▼
index.html  ← пустая оболочка: <div id="root"></div> + <script src="/src/main.tsx">
        │
        ▼
main.tsx  ← точка входа React:
  createRoot(...).render(
    <StrictMode>
      <BrowserRouter>        ← роутер «перехватывает» URL и решает, что показывать
        <AuthProvider>       ← контекст авторизации (глобальное состояние)
          <App />            ← корневой компонент: сайдбар + роуты страниц
```

В `App.tsx`:
- если **авторизация отключена** (`VITE_AUTH_REQUIRED !== 'false'` не задан) и токена нет — рендерится только страница `/login` (через `AUTH_REQUIRED` из AuthContext);
- иначе — каркас с боковым сайдбаром (10 пунктов меню) и `<Routes>` для 14 страниц;
- активный пункт меню подсвечивается через `useLocation()`.

### 2.4. API-слой (`src/api/client.ts`)

Единственный файл, через который фронтенд общается с бэкендом. Три механизма:

1. **`API_BASE`** — выбор базового URL:
   ```ts
   const API_BASE =
     import.meta.env.VITE_API_BASE ||            // явная переопределка через env
     (import.meta.env.DEV ? 'http://localhost:8000/v1' : '/v1')
   ```
   В dev-режиме — прямой адрес бэкенда, в проде — относительный путь `/v1`, который проксирует nginx.

2. **axios-инстанс `http`**:
   - в **request-интерцепторе** подставляет `Authorization: Bearer <token>` из `localStorage` (ключ `support_ai_token`);
   - в **response-интерцепторе** достаёт человекочитаемое сообщение об ошибке из `detail`/`message` и превращает в `Error`.

3. **Типизированные обёртки** — объекты `conversations`, `documents`, `tickets`, `dashboard`, `admin` с методами на каждый endpoint. Все типы данных (интерфейсы `Conversation`, `Message`, `FlowDebug`, `Intent`, `DocType`...) объявлены рядом — фронтенд полностью типизирован и «знает» форму ответов API.

Интересные детали:
- **API-ключ**: при наличии `VITE_API_KEY` / `VITE_ADMIN_API_KEY` в заголовки добавляется `X-API-Key` — это запасной способ авторизации для интеграций (например, для сборки в Docker, где входа по паролю нет).
- **Стриминг**: метод `sendMessageStream` использует **нативный `fetch`** (не axios), т.к. нужно читать ответ как поток (SSE — Server-Sent Events).

### 2.5. Авторизация (`src/contexts/AuthContext.tsx`)

Реализована через **React Context** + `localStorage`:

```
Login → POST /auth/login {username, password}
      → {access_token, user}
      → токен в localStorage, user в состоянии
```

- При старте приложения `AuthProvider` проверяет токен через `GET /auth/me`;
- если токен протух — чистит `localStorage` и возвращает на `/login`;
- `AUTH_REQUIRED` (env-переменная) позволяет **полностью отключить** авторизацию — удобно для локальных сборок/Docker;
- токен хранится в `localStorage` (не в cookie) — проще, но чуть менее безопасно против XSS; для админ-панели это приемлемый компромисс.

### 2.6. Ключевой сценарий: чат со стримингом (`ConversationDetail.tsx`)

Самая сложная страница. Механика:

1. Загрузка беседы: `conversations.get(id)` → массив сообщений.
2. Отправка сообщения:
   - **обычный режим**: `POST /conversations/{id}/messages` → ждём полный ответ → перезагружаем беседу;
   - **стриминг (SSE)**: `POST /conversations/{id}/messages:stream` → читаем ответ порциями через `reader.read()` (Web Streams API), накапливаем буфер, разбиваем по `\n\n` (границы SSE-событий), парсим `data:`-строки:
     ```ts
     const m = ev.match(/^data:\s*(.+)$/m)
     const data = JSON.parse(m[1])
     if (data.type === 'content') setStreamingContent((prev) => prev + (data.data || ''))
     else if (data.type === 'done') break
     ```
     Так ответ LLM появляется «по мере генерации», а не целиком.
3. **Debug-панель** (`FlowDebugPanel`) — «витрина explainability» RAG-пайплайна: для каждого ответа бота можно раскрыть:
   - решение (`decision`, `confidence`, `termination_reason`, `stage_reasons` — таймлайн фаз);
   - метрики ретрива (BM25/vector/merged/reranked), evidence-чанки со скором и сниппетами;
   - превью промптов (system/user) и полный лог LLM-вызовов (промпт → ответ, модель, токены, стоимость);
   - результат reviewer'а (claim → citations), self-critic, final polish;
   - `llm_usage_breakdown` — сколько и на какой модели потрачено.

   По сути, фронтенд визуализирует поле `debug` из API (`FlowDebug` — интерфейс из `client.ts`) — это ключевая фича для отладки качества ответов.

### 2.7. Остальные страницы (кратко)

- **Dashboard** — карточки метрик из `GET /dashboard/stats` (фильтрует ключи с префиксом `support_ai_`), форматирует числа (K/M).
- **Documents** — таблица документов базы знаний, CRUD, загрузка файлов (`FormData` + multipart), fetch по URL, краулинг сайта, re-crawl.
- **Tickets** — тикеты WHMCS: список, детали, статус одобрения (`pending/approved/rejected`) — через `admin.updateTicketApproval`.
- **Crawler** — управление WHMCS-краулером: сохранение session-куки, проверка кук с debug-инфо, запуск краула.
- **Settings** — конфигурация из БД: LLM-модель/ключ/base_url, system prompt (+ авто-генерация брендинга по URL), фича-флаги Archi v3 (13 тумблеров), очистка кэшей.
- **Intents / Doc Types / ApiTokens / ApiReference** — CRUD-экраны для соответствующих сущностей.

Общий паттерн страниц: `useState` для данных → `useEffect` для загрузки → состояние `loading/error/data` → рендер скелетона/ошибки/контента. Многие экраны повторяют этот шаблон (см. 2.9).

### 2.8. Dev-режим: как фронтенд ходит в бэкенд при разработке

В `vite.config.ts` настроен **прокси**: dev-сервер на `5173` перенаправляет запросы:

```
/v1/*  →  http://localhost:8000/v1/*   (или VITE_API_TARGET)
/docs, /openapi.json, /redoc  →  тот же бэкенд
```

Зачем: браузер не может слать запросы на другой порт/домен без CORS-настроек. Прокси позволяет фронтенду обращаться к бэкенду «как к своему» (относительные пути), и CORS не нужен. В проде ту же роль выполняет nginx.

### 2.9. Продакшен-сборка и деплой

**Multi-stage Dockerfile**:

```
Stage 1 «builder» (debian + Node 20):
  npm ci → npm run build (tsc && vite build) → dist/

Stage 2 (nginx:alpine):
  копируем dist/ в /usr/share/nginx/html
  копируем nginx.conf
  EXPOSE 80
```

**nginx.conf** решает две задачи:
1. **SPA-фолбэк**: `try_files $uri $uri/ /index.html` — любой URL отдаёт `index.html`, а маршрутизацией занимается React Router на клиенте. Без этого строка обновления на `/settings` давала бы 404.
2. **Прокси API**: `/v1/` и `/openapi.json` → `http://api:8000` (внутреннее имя сервиса в docker-compose), с пробросом заголовков `X-API-Key`.

В `docker-compose.yml` сервис `frontend` собирается из этого Dockerfile, а общий `nginx/nginx.conf` (в корне) уже проксирует снаружи к фронтенду и API.

## Часть 3. Оценка качества и наблюдения

### 3.1. Что сделано хорошо

1. **Полная типизация** — `client.ts` содержит все интерфейсы ответов API; `strict`-режим TS включён. Минимизирует рассинхрон фронта и бэкенда.
2. **Единый API-слой** — все запросы проходят через один axios-инстанс (токен, ошибки, base URL — в одном месте).
3. **Debug-панель** — редкая и ценная фича: интерфейс раскрывает внутренности RAG-пайплайна (промпты, токены, стоимость, evidence). Позволяет не-разработчику видеть, «почему бот так ответил».
4. **Стриминг** реализован аккуратно — с буфером и парсингом SSE-событий вручную, без тяжёлых библиотек.
5. **Красивый и консистентный UI** — Tailwind-токены вынесены в `@theme`, переиспользуемые классы (`glass`, `btn-primary`, `input-glass`) — в `index.css`.
6. **Правильный деплой** — multi-stage Dockerfile, SPA-фолбэк, прокси API.

### 3.2. Слабые места и точки роста

1. **Нет тестов** — во всём `frontend/` нет ни одного теста (ни unit, ни e2e). Для сравнения: бэкенд покрыт pytest. Стоит добавить как минимум тесты на API-клиент и ключевые страницы (Vitest + Testing Library) и e2e (Playwright).
2. **Дублирование состояния** — во многих страницах повторяется паттерн `loading/error/data` + ручные `load()`-функции. Напрашивается кастомный хук `useAsync` или `react-query` (кэширование, retry, invalidation).
3. **Раздутые страницы** — `ConversationDetail.tsx` (669 строк) и `Settings.tsx` (601 строка) смешивают разметку, логику и мелкие компоненты. Их стоит разбить: `MessageBubble`, `FlowDebugPanel`, `ToggleRow` уже вынесены, но в целом компоненты стоит дробить дальше.
4. **Дублирование между `api()` и прямыми вызовами `http`** — часть методов идёт через обёртку `api()`, часть — напрямую через `http.*.then(r => r.data)` (в `admin`). Лучше унифицировать.
5. **Токен в localStorage** — уязвим к XSS. Для админки приемлемо, но можно рассмотреть httpOnly-cookie.
6. **`noUncheckedSideEffectImports` и прочие строгие флаги** уже включены — хорошо, но часть кода (например, `catch {}` в стриминге) молча глотает ошибки парсинга.
7. **Нет i18n** — весь UI на английском; для multi-tenant продукта может понадобиться локализация.
8. **Тёмная тема захардкожена** — `index.html` имеет класс `dark`, цвета — в токенах. Динамическая смена темы не предусмотрена.

### 3.3. Рекомендации

1. Подключить **Vitest + React Testing Library** для компонентов и **Playwright** для e2e-сценариев (логин → чат → стриминг).
2. Ввести хук `useApi<T>(fetcher)` или библиотеку **TanStack Query** — уберёт ручной `loading/error`.
3. Разбить крупные страницы на директории: `components/`, `hooks/`, `types/`.
4. Унифицировать API-клиент: одна обёртка, один стиль.
5. Добавить базовые **aria-атрибуты** и проверку контраста — сейчас есть `role="switch"` и `aria-checked` в ToggleRow, но не везде.
6. Держать типы API в одном месте (уже так) и, по возможности, генерировать их из OpenAPI-схемы бэкенда (openapi-typescript), чтобы исключить ручной рассинхрон.
