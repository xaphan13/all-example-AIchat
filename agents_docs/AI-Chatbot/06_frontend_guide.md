## 1. Что такое «фронтенд» вообще

**Фронтенд** (frontend, «клиентская часть») — это всё, что видит и с чем взаимодействует
пользователь в браузере: страницы, формы, кнопки, анимации, чат. Технически это код,
который в итоге исполняется браузером и описывается тремя базовыми технологиями:

| Технология | Роль | Пример |
|---|---|---|
| **HTML** (HyperText Markup Language) | Структура и содержимое страницы | `<h1>Заголовок</h1>`, `<form>`, `<div>` |
| **CSS** (Cascading Style Sheets) | Внешний вид: цвета, шрифты, сетки, анимации | `background: purple;`, `display: flex;` |
| **JavaScript (JS)** | Поведение: обработка кликов, отправка запросов, обновление страницы без перезагрузки | `fetch('/api/chat', ...)`, `addEventListener` |

Браузер получает от сервера (или из сборки) HTML + CSS + JS, парсит их и «рисует»
страницу на экране. **Любой** современный фронтенд — React, Vue, Vite, Jinja2 — в конечном
счёте сводится к генерации именно этих трёх вещей. Разница лишь в том, **кто и когда их
генерирует**: сервер или браузер, заранее или на лету, вручную или с помощью фреймворка.

### Как браузер превращает код в картинку

1. Браузер запрашивает URL (`GET /`) и получает HTML-документ.
2. Парсер HTML строит **DOM** (Document Object Model) — дерево объектов страницы.
3. Парсер CSS применяет стили (CSSOM) и вычисляет геометрию элементов (**layout**).
4. Браузер отрисовывает картинку (**paint**) и обновляет её при изменениях.
5. JavaScript-код может менять DOM и CSS «на лету» — браузер перерисовывает затронутую часть.

## 2. Кто генерирует HTML: сервер или браузер?

Это главный водораздел, по которому различаются все технологии. Есть два базовых подхода:

### 2.1. SSR / MPA — серверная генерация (как в этом проекте)

**SSR** (Server-Side Rendering) — HTML собирается **на сервере** и приходит в браузер готовым.
Каждая страница — отдельный HTML-документ, переходы между страницами — полная перезагрузка
(так устроен классический веб с 1990-х). Такую архитектуру называют **MPA**
(Multi-Page Application).

```
Браузер ──GET /─────► Сервер
Браузер ◄──HTML─────── Сервер   ← страница уже полностью собрана
Браузер ──GET /chat─► Сервер
Браузер ◄──HTML─────── Сервер   ← снова полная загрузка
```

- **Плюсы:** быстрый первый экран, хорошо индексируется поисковиками (SEO), не требует
  тяжёлых клиентских скриптов, проще в разработке.
- **Минусы:** каждый переход — полная перезагрузка страницы (чуть медленнее ощущается),
  сервер несёт нагрузку по генерации HTML, интерактивность ограничена.
- **Примеры инструментов:** Jinja2, Django Templates, Thymeleaf, Rails ERB, Blade (PHP).

### 2.2. CSR / SPA — генерация в браузере

**CSR** (Client-Side Rendering) — сервер отдаёт «пустую оболочку» (`<div id="root"></div>`
+ один JS-файл), а **JavaScript уже в браузере** строит весь интерфейс и подгружает данные
по API. Такое приложение называют **SPA** (Single Page Application): после первой загрузки
переходы между «страницами» происходят без перезагрузки — JS меняет содержимое.

```
Браузер ──GET /──────► Сервер
Браузер ◄──shell+JS─── Сервер   ← пустая оболочка + код приложения
Браузер ──GET /api/…─► Сервер   ← данные подтягиваются через API (JSON)
Браузер ◄──JSON─────── Сервер
```

- **Плюсы:** плавный, «нативный» UX без миганий при переходах; сервер отдаёт только JSON —
  удобно для мобильных приложений и API.
- **Минусы:** медленный первый экран (браузер должен скачать и выполнить JS до появления
  контента), сложнее SEO, больше кода и зависимостей.
- **Примеры инструментов:** React, Vue, Angular, Svelte — всё это библиотеки/фреймворки,
  из которых собирают SPA.

### 2.3. Промежуточные подходы

- **SSG** (Static Site Generation) — HTML собирается **один раз при сборке** (build-time)
  в статические файлы и раздаётся без сервера вообще. Быстро и дёшево, но контент
  обновляется только при пересборке. Примеры: Astro, Next.js `generateStaticParams`, Hugo.
- **ISR** (Incremental Static Regeneration) — гибрид SSG + SSR: страницы генерируются
  статически, но по расписанию или по запросу пересобираются заново. Концепция Next.js.
- **Гибридные / «изоморфные» приложения** — сервер отдаёт готовый HTML (SSR), а затем
  JS «оживляет» страницу и продолжает работать как SPA (**hydration**). Так работают
  Next.js, Nuxt, SvelteKit.

> **Где здесь наш проект?** Это чистый SSR/MPA: FastAPI генерирует HTML через Jinja2,
> браузер получает готовые страницы, а JS используется только для отдельных интерактивных
> кусочков (отправка формы чата через `fetch`, анимации).

## 3. Шаблонизаторы: Jinja2 и другие

**Шаблонизатор** (template engine) — библиотека, которая берёт HTML-заготовку с
плейсхолдерами и подставляет в неё данные, получая готовую страницу. Это способ делать
SSR-разметку удобно: без шаблонизатора пришлось бы склеивать строки вручную.

### Jinja2 — то, что использует этот проект

**Jinja2** — шаблонизатор для **Python**. Он используется Flask, FastAPI (через обёртку
`Jinja2Templates` из Starlette) и многими другими.

Синтаксис — три вида конструкций:

```jinja2
<!-- Вывод значения -->
<p>{{ user.email }}</p>

<!-- Условия и циклы -->
{% if user.is_active %}
    <p>Активен</p>
{% endif %}

{% for message in messages %}
    <div>{{ message.text }}</div>
{% endfor %}

<!-- Наследование шаблонов (layout + блоки) -->
{% extends "base.html" %}
{% block content %} ... {% endblock %}
```

В этом проекте Jinja2 используется в его самой простой форме — шаблоны статические, без
переменных из Python (контекст — только `request`):

```python
# app/main.py
templates = Jinja2Templates(directory="app/templates")

@app.get("/")
async def landing_page(request: Request):
    return templates.TemplateResponse("landing.html", {"request": request})
```

**Автоэкранирование** — ключевая особенность Jinja2: при выводе `{{ value }}` специальные
символы (`<`, `>`, `&`) экранируются автоматически, что защищает от XSS. Подробнее об
XSS в отчёте по проекту (`docs/07_frontend_project_report.md`).

### Другие шаблонизаторы

| Шаблонизатор | Язык | Где встречается |
|---|---|---|
| **Django Templates** | Python | Фреймворк Django (свой, отдельный от Jinja2) |
| **ERB** | Ruby | Rails |
| **Blade** | PHP | Laravel |
| **Thymeleaf** | Java | Spring Boot |
| **Pug / Jade** | Node.js | Express (компактный синтаксис с отступами вместо тегов) |
| **EJS, Handlebars, Nunjucks** | JavaScript | Node.js SSR |

> **Вывод:** шаблонизаторы — это инструменты именно для SSR/MPA. Если вы переезжаете
> на React/Vue, шаблонизаторы в этой роли обычно не нужны — разметка пишется на JSX/шаблонах
> внутри самого компонента и собирается клиентским кодом.

## 4. JavaScript-фреймворки: React, Vue, Svelte, Angular

Когда в браузере нужно строить сложный интерактивный интерфейс (динамические списки,
формы, состояния, обновления без перезагрузки), писать всё вручную через
`document.getElementById(...)` становится тяжело. Для этого существуют **фреймворки и
библиотеки**, которые декларативно описывают интерфейс: вы говорите «вот как должно
выглядеть при таких данных», а фреймворк сам обновляет DOM при изменении данных.

### 4.1. React — «царь» экосистемы

- **Кто:** библиотека (не фреймворк) от Meta, 2013 г. Самая популярная.
- **Идея:** декларативность + компоненты. Интерфейс разбивается на переиспользуемые
  **компоненты** — функции, возвращающие разметку.
- **JSX** — синтаксис, в котором HTML пишется прямо внутри JavaScript:

```jsx
function MessageBubble({ text, sender }) {
  return (
    <div className={sender === 'user' ? 'justify-end' : 'justify-start'}>
      <p>{text}</p>
    </div>
  );
}
```

- **Virtual DOM:** React хранит своё виртуальное дерево элементов, при изменении данных
  сравнивает его с предыдущим и точечно обновляет только изменившиеся части настоящего DOM.
- **Состояние и хуки:** `useState`, `useEffect`, `useContext` и др. — функции для управления
  состоянием компонента и побочными эффектами (запросы, таймеры).
- **Экосистема:** Next.js (SSR/SSG мета-фреймворк), React Router, Redux/Zustand (состояние),
  React Query (данные с сервера).

### 4.2. Vue — «золотая середина»

- **Кто:** фреймворк от Эвана Ю, 2014 г. Популярен, сочетает лёгкость и полноту.
- **SFC (Single-File Components):** один компонент = один файл `.vue` с тремя секциями:
  `<template>`, `<script>`, `<style>`.
- **Реактивность:** вместо Virtual DOM-диффинга Vue отслеживает зависимости данных и
  обновляет DOM точнее и быстрее (Vue 3 на Proxy).

```vue
<template>
  <p>{{ message }}</p>
</template>

<script setup>
import { ref } from 'vue'
const message = ref('Привет из Vue!')
</script>
```

- **Экосистема:** Nuxt (мета-фреймворк), Pinia (состояние), Vue Router.

### 4.3. Svelte — «фреймворк, который исчезает»

- **Идея:** никакого Virtual DOM и рантайма в браузере. Компилятор превращает компоненты
  в оптимизированный чистый JavaScript, который напрямую обновляет DOM.
- Результат — маленькие бандлы и высокая скорость. Мета-фреймворк — SvelteKit.

### 4.4. Angular — «тяжёлая артиллерия»

- Полноценный фреймворк от Google (TypeScript с рождения): маршрутизация, DI, формы,
  HTTP-клиент — всё «в коробке». Крутая кривая обучения, много boilerplate, но мощный
  для больших корпоративных приложений.

### 4.5. Solid, Preact, Qwik и другие

- **Preact** — ультра-лёгкий клон React (~3 КБ).
- **Solid** — реактивность как у Svelte, но JSX как у React.
- **Qwik** — «resumability»: приложение разбивается на куски и загружается по мере надобности.

### Какой фреймворк выбрать?

| Критерий | React | Vue | Svelte | Angular |
|---|---|---|---|---|
| Сложность обучения | Средняя | Низкая | Низкая | Высокая |
| Размер экосистемы | Огромная | Большая | Растущая | Большая |
| Рантайм в браузере | Virtual DOM | Реактивность + VDOM | Нет (компилятор) | Change detection |
| Типичный сценарий | SPA, SSR, мобильные (React Native) | SPA, SSR, простые проекты | Лёгкие быстрые приложения | Крупный enterprise |

## 5. Сборщики и инструменты сборки: Vite, Webpack и другие

Фреймворки пишутся на современном JavaScript (JSX, TypeScript, ESM, CSS-препроцессоры),
который **браузеры не понимают напрямую**. Нужен **сборщик** (bundler) — программа,
которая берёт исходники и превращает их в готовые файлы для браузера: объединяет модули,
транспилирует синтаксис, минифицирует, подключает стили, картинки.

### 5.1. Vite — современный стандарт

**Vite** (фр. «быстро») — инструмент сборки от автора Vue (Эван Ю), 2020 г. Сейчас —
де-факто стандарт для старта новых проектов на React/Vue/Svelte и т.д.

**Ключевые особенности:**

1. **Dev-сервер без «упаковки» (no-bundling dev).** Vite отдаёт исходные ES-модули
   браузеру напрямую, а тяжелые зависимости (React, Vue) пре-бандлит esbuild'ом.
   Сервер стартует за миллисекунды, а не десятки секунд, как Webpack.

2. **HMR (Hot Module Replacement).** При изменении файла Vite обновляет **только этот
   модуль** в открытом браузере, сохраняя состояние приложения. Не перезагружает страницу.

3. **Production-сборка** выполняется через **Rollup** — объединяет всё в оптимизированные
   бандлы с tree-shaking (выкидывание неиспользуемого кода), минификацией, кэш-хэшами.

```
npm create vite@latest my-app -- --template react
npm install
npm run dev        # dev-сервер с HMR (http://localhost:5173)
npm run build      # production-сборка в dist/
npm run preview    # локальный просмотр собранного
```

### 5.2. Webpack — «взрослый» предшественник

- Самый мощный и гибкий сборщик, конфиг `webpack.config.js`. Именно он лежит под
  Create React App. Гибкость = сложность: конфигурация большая, сборка медленная.
- Идеи Webpack (loaders, plugins, HMR, code splitting) стали каноном, но Vite проще.

### 5.3. Другие инструменты

| Инструмент | Тип | Назначение |
|---|---|---|
| **esbuild** | Бандлер на Go | Сверхбыстрый, используется Vite внутри dev-режима |
| **Rollup** | Бандлер ESM | Сборка библиотек, production-часть Vite |
| **Turbopack** | Бандлер на Rust | Преемник Webpack от создателей Next.js (используется в Next 15+) |
| **Parcel** | Бандлер | «Zero config» — работает без конфигурации |
| **Babel** | Транспилятор | Превращает JSX и новейший JS в совместимый код |
| **SWC** | Транспилятор на Rust | Быстрая замена Babel (используется в Next.js и Vite) |

### 5.4. Мета-фреймворки: Next.js, Nuxt, SvelteKit

Фреймворки (React/Vue/Svelte) сами по себе умеют только «рисовать интерфейс в браузере»
(CSR). Чтобы получить SSR, маршрутизацию, SSG — поверх них строят **мета-фреймворки**:

| Мета-фреймворк | Основа | Особенность |
|---|---|---|
| **Next.js** | React | SSR/SSG/ISR, App Router, серверные компоненты, API-роуты |
| **Nuxt** | Vue | SSR/SSG, модульная система, автоподключение компонентов |
| **SvelteKit** | Svelte | SSR, адаптеры под любой хостинг |
| **Remix** | React | SSR с упором на нативные веб-стандарты |
| **Astro** | Мульти-фреймворк | «Islands»: статика + островки интерактива, почти без JS |

> Интересный факт: Next.js/Nuxt делают **ровно то же**, что сейчас делает наш проект на
> FastAPI + Jinja2 (HTML с сервера), но на JavaScript. Разница — глубина интерактивности
> и то, какой язык пишет серверную часть.

## 6. Экосистема JavaScript-разработки: npm, package.json, TypeScript

Чтобы понимать статьи про Vite/React, нужно знать базовые понятия:

- **Node.js** — рантайм JavaScript вне браузера. На нём работают все сборщики и dev-серверы.
- **npm / yarn / pnpm / bun** — менеджеры пакетов. `npm install <pkg>` скачивает зависимости.
- **`package.json`** — манифест проекта: зависимости, скрипты (`dev`, `build`), метаданные.
  Аналог `pyproject.toml` в Python-мире.
- **`node_modules/`** — папка с установленными пакетами (аналог `.venv/` у Python).
- **TypeScript** — JavaScript с типами. Пишется на нём, компилируется в обычный JS.
  Де-факто стандарт для новых проектов: ранний отлов ошибок, автокомплит, безопасный
  рефакторинг. Аналог mypy/Pydantic в Python.
- **JSX** — синтаксис React (HTML внутри JS). Vue использует шаблоны, Angular — тоже.

## 7. CSS-подходы: от чистого CSS до Tailwind

Стили можно писать по-разному:

| Подход | Идея | Пример |
|---|---|---|
| **Чистый CSS** | Классы + селекторы в `.css`-файлах | `.btn { background: purple; }` |
| **CSS-препроцессоры (SCSS/Sass/Less)** | Переменные, вложенность, миксины, компилируются в CSS | `$primary: purple;` |
| **CSS Modules** | Локальные (захешированные) имена классов, сборщик изолирует стили | `import styles from './x.module.css'` |
| **CSS-in-JS (styled-components)** | Стили пишутся в JS и генерируются динамически | `styled.button\`background: purple;\`` |
| **Utility-first (Tailwind CSS)** | Готовые утилитарные классы прямо в HTML | `class="bg-purple-500 px-4 py-2 rounded-lg"` |
| **UI-библиотеки (Bootstrap, Material)** | Готовые компоненты и темы | `class="btn btn-primary"` |

### Tailwind CSS — то, что использует наш проект

**Tailwind** — «utility-first» CSS-фреймворк: вы не пишете свои классы, а комбинируете
готовые утилиты (`bg-purple-500`, `rounded-2xl`, `p-6`, `flex`). Это быстро, консистентно,
и HTML получается самодокументируемым.

Важно: в этом проекте Tailwind подключён через **CDN**:

```html
<script src="https://cdn.tailwindcss.com"></script>
```

Это означает, что Tailwind компилирует стили **прямо в браузере** при каждой загрузке
страницы (runtime-компиляция, ~300 КБ JS). Удобно для прототипа, но медленно. «Правильный»
путь — сборка: Tailwind CLI (или плагин в Vite/Webpack) заранее сканирует HTML и
генерирует минифицированный `.css`-файл.

## 8. Как всё это соотносится с нашим проектом

Сводная таблица «мир SSR vs мир SPA»:

| Вопрос | Наш проект (SSR/MPA) | «Модный» стек (SPA) |
|---|---|---|
| HTML генерирует | **Сервер** (Python, Jinja2) | **Браузер** (JS) или сервер (Next/Nuxt) |
| Бэкенд | FastAPI | Node.js (Next API routes) или отдельный API (FastAPI) |
| Разметка | Jinja2-шаблоны | JSX (React) / SFC (Vue) |
| Стили | Tailwind CDN | Tailwind (сборка), CSS Modules, SCSS |
| Сборка | Не нужна | Vite / Webpack |
| «Компоненты» | Дублируемые куски HTML + `{% include %}` | Настоящие компоненты с состоянием |
| Интерактив | Отдельные `<script>` на странице | Один JS-рантайм приложения |
| Переходы между страницами | Полная перезагрузка | Бесшовные (SPA-роутинг) |
| Данные в браузере | HTML + fetch для отдельных действий | fetch к REST/GraphQL, кэширование на клиенте |

## 9. Мини-словарь терминов

| Термин | Что значит |
|---|---|

## 10. Резюме

1. **Любой** фронтенд в итоге — это HTML + CSS + JS.
2. Разница технологий — в том, **кто и когда** генерирует HTML: сервер (SSR/Jinja2/Django)
   или браузер (CSR/React/Vue).
3. **Jinja2** — шаблонизатор Python для SSR. В нашем проекте — основной инструмент фронтенда.
4. **React/Vue/Svelte/Angular** — библиотеки/фреймворки для сложного клиентского
   интерфейса; обычно используются в связке со сборщиком.
5. **Vite** — быстрый сборщик и dev-сервер (HMR), современный стандарт для старта проектов
   на этих фреймворках.
6. **Tailwind** — utility-first CSS; в проекте используется в «CDN»-режиме, что годится
   только для прототипов.
7. Переезд на React/Vue имеет смысл, когда интерактивность страницы перерастает
   возможности простых `<script>`-блоков — иначе SSR с шаблонизатором проще и быстрее.
