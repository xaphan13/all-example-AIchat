# Отчёт о работе приложения с AI-моделями

## 1. Краткое резюме

AI Chatbot Assistant — монолитное веб-приложение на FastAPI с серверным рендерингом Jinja2-шаблонов. AI-функция реализована как один защищённый HTTP-эндпоинт `POST /api/chat`.

На текущем этапе приложение:

- принимает текст пользователя в браузере;
- передаёт его в сервис `app/services/chat.py`;
- вызывает GitHub Models API через асинхронный SDK `openai`;
- использует модель `openai/gpt-4o`;
- возвращает клиенту один готовый текстовый ответ;
- не хранит историю беседы и не выполняет несколько AI-задач самостоятельно.

Это рабочий сценарий «один запрос — один ответ», а не полноценная агентная платформа.

## 2. Архитектура AI-взаимодействия

Поток данных выглядит так:

```text
Пользователь
    │
    │  браузерный fetch: POST /api/chat
    │  JSON: {"prompt": "..."}
    ▼
FastAPI: app/api/v1/chat.py
    │
    │  проверка cookie/JWT и Pydantic-схемы ChatRequest
    ▼
Сервис: app/services/chat.py
    │
    │  формирование сообщения
    │  AsyncOpenAI.chat.completions.create(...)
    ▼
GitHub Models API
    │  https://models.github.ai/inference/
    │  Bearer-токен из GITHUB_TOKEN
    ▼
Ответ модели
    │
    │  choices[0].message.content
    ▼
JSON: {"response": "..."}
    ▼
Браузер отображает ответ в чате
```

Связанные файлы:

| Компонент | Файл | Ответственность |
|---|---|---|
| AI-клиент | `app/services/chat.py` | Создание `AsyncOpenAI` и вызов модели |
| API-маршрут | `app/api/v1/chat.py` | Валидация запроса, авторизация, JSON-ответ |
| DTO запроса | `app/schemas/chat.py` | Поле `prompt: str` |
| Веб-интерфейс | `app/templates/index.html` | Отправка сообщений и отображение ответа |
| Конфигурация | `app/core/config.py` | `GITHUB_TOKEN` и общие настройки |

## 3. Как происходит общение с нейронной сетью

### 3.1. Формат запроса от браузера к приложению

После авторизации JavaScript отправляет HTTP-запрос:

```http
POST /api/chat HTTP/1.1
Content-Type: application/json
Cookie: fastapiusersauth=<JWT>

{"prompt":"Объясни async/await в Python"}
```

Тело запроса соответствует схеме `ChatRequest`. Cookie нужна, потому что маршрут защищён зависимостью `current_user`.

### 3.2. Формат запроса от приложения к провайдеру

Сервис преобразует пользовательский текст в список сообщений OpenAI Chat Completions API:

```python
messages=[
    {
        "role": "user",
        "content": "Hey ChatGPT, ..." + prompt,
    }
]
```

Затем SDK делает асинхронный HTTP-вызов к GitHub Models API. Авторизация выполняется через API-ключ, значение которого берётся из `GITHUB_TOKEN`.

### 3.3. Формат ответа

Провайдер возвращает объект, совместимый с OpenAI SDK. Приложение извлекает только первый вариант ответа:

```python
response.choices[0].message.content
```

Наружу отправляется упрощённый JSON:

```json
{
  "response": "Ответ AI-модели"
}
```

Метаданные генерации, количество токенов, причина завершения и альтернативные варианты ответа клиенту не передаются.

## 4. Какие возможности предлагает приложение

### Реализовано сейчас

1. **Чат с AI после авторизации.** Пользователь может отправлять текстовые запросы через веб-интерфейс.
2. **Асинхронный вызов модели.** Используется `AsyncOpenAI`, поэтому запрос к провайдеру не блокирует поток синхронным вызовом.
3. **OpenAI-compatible интеграция.** Приложение обращается к API через стандартный интерфейс `chat.completions` и сменный `base_url`.
4. **Typing indicator.** Браузер показывает индикатор ожидания ответа.
5. **Защита чата.** Доступ к странице `/chat` и API `/api/chat` требует аутентификации.
6. **Единый текстовый интерфейс.** Ответ модели отображается в виде сообщения в существующем чате.
7. **Автоматическая документация API.** FastAPI предоставляет Swagger UI по адресу `/docs`.

### Ограничения текущей реализации

- история сообщений не сохраняется в SQLite и не передаётся модели;
- каждый запрос не зависит от предыдущих сообщений;
- потоковая генерация через SSE или WebSocket отсутствует — ответ приходит целиком;
- модель, URL API и системная инструкция зашиты в `app/services/chat.py`;
- пользователь не может выбрать модель или провайдера через интерфейс;
- нет параметров `temperature`, `max_tokens` и других настроек генерации;
- нет таймаута и серверной обработки ошибок timeout, 429, 5xx и сетевых сбоев;
- системная инструкция и пользовательский ввод объединяются в одну строку;
- инструменты, function calling, поиск, загрузка файлов и RAG не реализованы;
- ответы не проверяются отдельным валидатором и не проходят модерацию;
- в интерфейсе используется `innerHTML` для текста ответа, что требует исправления во избежание XSS;
- тестовый набор для AI-интеграции отсутствует.

## 5. Возможно ли мультиагентное использование

### Ответ для текущей версии

Готового мультиагентного режима **нет**. Сейчас приложение не содержит:

- оркестратора, который распределяет задачу между агентами;
- нескольких ролей или специализированных системных промптов;
- механизма передачи результата одного агента другому;
- параллельного запуска нескольких AI-вызовов;
- общей памяти или хранилища состояния задачи;
- маршрутизации к разным моделям;
- инструментов, которыми агенты могли бы пользоваться самостоятельно;
- контроля лимитов, циклов и критериев завершения.

Один пользовательский запрос приводит к одному вызову одной модели.

### Как это можно добавить

Мультиагентность совместима с текущей архитектурой, но потребует нового слоя оркестрации. Минимальная схема:

```text
POST /api/agent-task
    │
    ▼
Оркестратор
    ├── Planner: разбивает задачу
    ├── Researcher: собирает факты
    ├── Writer: готовит результат
    └── Reviewer: проверяет результат
    │
    ▼
Итоговый ответ пользователю
```

Для реализации потребуется:

1. выделить интерфейс провайдера/агента;
2. описать роли и системные инструкции отдельно;
3. хранить состояние задачи и сообщения агентов;
4. добавить последовательный или параллельный запуск через `asyncio.gather`;
5. определить лимиты итераций, токенов, времени и стоимости;
6. добавить обработку отказа одного агента;
7. реализовать авторизацию инструментов и проверку внешних действий;
8. при необходимости сохранять `Conversation`, `AgentRun` и `Message` в БД.

Подробный проектный пример приведён в `docs/09_ai_code_examples.md`. Он является примером будущего расширения, а не частью текущего приложения.

## 6. Безопасность и эксплуатационные замечания

- `GITHUB_TOKEN` нельзя помещать во frontend или коммитить в репозиторий.
- Для production следует заменить небезопасное значение по умолчанию `SECRET` и задавать его через окружение.
- Пользовательский ввод нельзя считать доверенным системным контекстом: нужно разделять `system` и `user` messages.
- Необходимо ограничить длину запроса, добавить rate limiting и таймаут вызова провайдера.
- Ошибки провайдера следует преобразовывать в понятные HTTP-ответы, не раскрывая токены и внутренние трассировки.
- Текст, пришедший от модели, следует добавлять через `textContent` либо безопасный Markdown-рендерер с санитизацией, а не напрямую через `innerHTML`.
- При добавлении мультиагентов каждый инструмент должен иметь явные разрешения и аудит действий.

## 7. Итоговая оценка

Текущая AI-функциональность — компактная интеграция одного FastAPI-сервиса с GitHub Models через OpenAI-совместимый API. Она подходит для демонстрационного чат-бота и MVP, но ещё не предоставляет память диалога, выбор моделей, streaming, инструменты или мультиагентное выполнение. Основные направления развития: конфигурируемый AI-клиент, история сообщений, обработка ошибок, потоковая выдача и отдельный оркестратор агентов.
