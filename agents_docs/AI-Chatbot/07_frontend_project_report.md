# 07 — Отчёт по фронтенду проекта AI Chatbot Assistant

> Отчёт анализирует текущую реализацию фронтенда (SSR на Jinja2 + Tailwind CDN +
> ванильный JS), описывает, как всё работает, и даёт рекомендации.
> Образовательная справка «как вообще устроен фронтенд» — в `docs/06_frontend_guide.md`.

## 1. Общая картина

### 1.1. Стек фронтенда

| Слой | Технология | Статус |
|---|---|---|
| Рендеринг HTML | **Jinja2** (SSR, через FastAPI/Starlette) | ✅ работает |
| Сервер | FastAPI (Python) | ✅ работает |
| Стили | **Tailwind CSS** через CDN (`cdn.tailwindcss.com`) | ⚠️ прототипный режим |
| Иконки | **Lucide** через CDN (`unpkg.com/lucide`) | ✅ работает |
| Интерактивность | **Ванильный JavaScript** (`<script>` внутри шаблонов) | ✅ работает |
| Сборка/бандлинг | **Отсутствует** (CDN-зависимости, статические шаблоны) | — |
| Статические файлы | `app/static/` заявлена, но **директория не существует** | ❌ сломано |

### 1.2. Архитектура: классический SSR (MPA)

Проект — классическое **многостраничное SSR-приложение**: сервер по каждому маршруту
отдаёт готовый HTML-документ, браузер лишь «оживляет» его небольшим JS. Это полностью
симметрично подходу Django/Rails/Spring — и является осознанным, простым и адекватным
выбором для MVP.

```
GET /        → landing.html   (лендинг, без JS-логики, кроме иконок)
GET /login   → login.html     (форма входа, JS: fetch /auth/login)
GET /signup  → signup.html    (форма регистрации, JS: fetch /auth/register)
GET /chat    → index.html     (чат, JS: fetch /api/chat, /auth/logout)
```

Все страницы отдаются через один экземпляр `Jinja2Templates` (`app/main.py:19`).
JS-код написан прямо в шаблонах; внешних `.js`/`.css` файлов нет.

## 2. Постраничный разбор

### 2.1. `landing.html` — лендинг

- **Назначение:** маркетинговая страница (Hero + Features + Footer), ссылки на `/login`,
  `/signup`, `/chat`.
- **JS:** только `lucide.createIcons()` — заменяет `<i data-lucide="...">` на SVG-иконки.
- **Стили:** ~45 строк кастомного CSS (анимации `gradientShift`, `float`; классы
  `glass-effect`, `btn-glow`) + Tailwind-классы в разметке.
- **Замечания:** ссылки «Features/Pricing/API/About» — пустые `href="#"`; не используется
  Jinja2-шаблонизация (контекст не передаётся) — шаблон мог бы быть статичным `.html`.

### 2.2. `login.html` — вход

- **Назначение:** форма email+password.
- **JS:** `fetch('/auth/login', ...)` с `Content-Type: application/x-www-form-urlencoded`
  и телом `username=<email>&password=<password>` (так ожидает FastAPI-Users OAuth2-формой).
  При `response.ok` — `window.location.href = '/chat'`, иначе — показ ошибки
  `errorData.detail`; при сетевой ошибке — `showError('Network error...')`.
- **Auth-механика:** бэкенд ставит HttpOnly-cookie `fastapiusersauth` (JWT), которая далее
  автоматически отправляется браузером со всеми запросами. JS с cookie напрямую не работает.
- **Замечания:** индикатор ошибки скрывается через 5 секунд; `response.ok` не проверяется
  по статусам 400/401 отдельно — но `detail` показывается корректно.

### 2.3. `signup.html` — регистрация

- **Назначение:** форма email + password + full_name.
- **JS:** `fetch('/auth/register', ...)` с `application/json` и телом
  `{ email, password, full_name }`. При успехе — сообщение + редирект на `/login` через 2 с;
  при ошибке — показ `data.detail` в красном блоке.
- **Замечания:** поле `fullName` не `required` — при пустом значении бэкенд вернёт ошибку
  валидации (в миграции `full_name` nullable — см. `docs/04_code_quality.md` #18).

### 2.4. `index.html` — чат (самая сложная страница)

Это единственный по-настоящему интерактивный экран. Разберём подробно.

**Статика:**
- `<style>` — ~80 строк: анимации появления сообщений (`fadeIn`), typing-индикатор
  (заголовок `::after` + три точки `typing-dots`), скрытие скроллбара, градиентный фон,
  glass-карточки, glow-эффекты.
- Tailwind-классы для всей геометрии (flex-контейнер чата, пузыри сообщений, форма ввода).

**Динамика (JS):**

| Функция/обработчик | Строки | Что делает |
|---|---|---|
| `lucide.createIcons()` | 162 | Рендер SVG-иконок (bot, settings, info, log-out, send, paperclip) |
| `textarea` `input` | 165-169 | Авто-высота textarea (до 128px) |
| `#chat-form` `submit` | 172-209 | Отправка сообщения: `fetch('/api/chat', {prompt})`, обработка 401 (редирект на `/login`), добавление ответа AI |
| `addMessage(text, sender)` | 211-238 | Создание DOM-узлов для пузыря сообщения, скролл вниз. **XSS-риск** — `innerHTML` (см. §5) |
| `showTypingIndicator()` | 240-261 | Показ анимированных трёх точек |
| `removeTypingIndicator()` | 263-266 | Удаление индикатора |
| `textarea` `keydown` | 269-274 | Enter = отправка, Shift+Enter = новая строка |
| `logout()` | 277-285 | `fetch('/auth/logout')` + редирект на `/` |

**Особенности UX:** при `401` браузер перенаправляется на `/login` — корректная реакция
на протухший JWT (lifetime 3600 c). При сетевой ошибке или ошибке LLM выводится
заглушка «Sorry, I encountered an error. Please try again.»

## 3. Взаимодействие с бэкендом

Фронтенд общается с сервером по **4 API-эндпоинтам**:

| Действие | Эндпоинт | Формат | Кто инициирует |
|---|---|---|---|
| Вход | `POST /auth/login` | `application/x-www-form-urlencoded` | `login.html` |
| Регистрация | `POST /auth/register` | `application/json` | `signup.html` |
| Отправка сообщения | `POST /api/chat` | `application/json` `{prompt}` | `index.html` |
| Выход | `POST /auth/logout` | — | `index.html` |

**Особенность:** аутентификация — cookie-сессия (`fastapiusersauth`), поэтому никакие
JS-заголовки авторизации не нужны: cookie отправляется браузером автоматически.
Для `POST /api/chat` обязательно `Content-Type: application/json` — это единственный
заголовок, который JS задаёт вручную.

**Ошибки:** 401 обрабатывается только в чате (редирект на `/login`). Для форм входа/
регистрации показываются тексты из `detail`. Единой клиентской обработки ошибок нет.

## 4. Наблюдения по коду

### Что сделано хорошо

1. **Правильный стек для задачи.** SSR на Jinja2 — минимальный и предсказуемый способ
   сделать 4 страницы + интерактивный чат. React/Vue здесь были бы избыточны.
2. **Никаких серверных данных в JS-логике** — шаблоны «тупые», весь обмен через HTTP,
   легко тестировать и переиспользовать.
3. **Приличный UX-минимум:** typing-индикатор, автовысота textarea, Enter-to-send,
   автоскролл, обработка 401.
4. **Скролл-анимации и glassmorphism** — аккуратно, без тяжёлых библиотек.
5. **Использование `textContent` для текста ошибок** (login/signup) — без XSS.

### Проблемы и риски

| # | Проблема | Где | Серьёзность |
|---|---|---|---|
| 1 | **XSS через `innerHTML`** в чате: текст от LLM вставляется как HTML. Если модель вернёт `<script>`/`<img onerror>` — он выполнится в браузере каждого пользователя | `index.html:224-227` | 🔴 Критично |
| 2 | **Tailwind через CDN** — runtime-компиляция ~300 КБ JS в браузере; медленный первый экран; в production недопустимо (частые обновления CDN-скрипта, нет стабильных версий, лишний сетевой запрос) | все шаблоны | 🟠 Высоко |
| 3 | **Дублирование CSS** между `landing/login/signup` (gradient-bg, glass-effect, btn-glow, floating) — нет `base.html` | 3 файла | 🟡 Средне |
| 4 | **Нет статики в проекте** — `app/static/` не существует, а `main.py` монтирует `StaticFiles` → приложение не стартует (см. `docs/04_code_quality.md` #1) | `app/main.py:20` | 🔴 Критично |
| 5 | **CDN-зависимости без версий** — `unpkg.com/lucide@latest` и `cdn.tailwindcss.com` могут обновляться без контроля | все шаблоны | 🟡 Средне |
| 6 | **Нет обратной связи при долгом запросе LLM** — typing-индикатор есть, но нет таймаута; при зависшем запросе индикатор будет крутиться вечно | `index.html:184-208` | 🟡 Средне |
| 7 | **Нет повторного использования кода**: скрипты и стили нельзя подключать постранично, JS «в шаблоне» — не переиспользуется | все шаблоны | 🟡 Средне |
| 8 | `lang="en"` у всех страниц, «мёртвые» ссылки `href="#"` на лендинге | шаблоны | 🟢 Низко |
| 9 | Нет защиты от двойной отправки формы (double-click) | `index.html` | 🟢 Низко |

## 5. Углублённо: XSS в чате

```js
bubbleDiv.innerHTML = `
    <p class="text-sm leading-relaxed">${text}</p>
    <p class="text-xs opacity-70 mt-2">${new Date().toLocaleTimeString()}</p>
`;
```

`text` — это ответ AI-модели, а в будущем, возможно, и любой пользовательский текст.
Если строка содержит HTML, он выполнится (вставка картинок, переходы, скрипты).
Так как чат многопользовательский (все логинятся в одно приложение), это вектор атаки.

**Исправление (минимальное):** собирать контент без `innerHTML` — через `textContent`:

```js
const p = document.createElement('p');
p.className = 'text-sm leading-relaxed';
p.textContent = text;   // никакой интерпретации HTML
bubbleDiv.appendChild(p);
```

Или, если нужен rich-text (markdown-разметка), использовать проверенную библиотеку
(sanitize + markdown), например `marked` + `DOMPurify`.

> Примечание: Jinja2 сам по себе экранирует `{{ }}`, но в этом проекте шаблоны
> не подставляют пользовательские данные на сервере — вся опасная вставка происходит
> в браузере через JS.

## 6. Сравнение: как выглядел бы этот фронтенд на React/Vue

Чтобы оценить текущий выбор, представим альтернативы.

### 6.1. Полный SPA (React/Vue + Vite + отдельный API)

- Все 4 экрана — компоненты одного SPA; данные подтягиваются через существующие эндпоинты.
- **Плюсы:** бесшовные переходы, единый код, удобная работа со состоянием чата.
- **Минусы:** +Node.js, +сборка, +роутер, +менеджер состояния, +TypeScript; первый экран
  станет медленнее (нужно скачать бандл); бэкенд остаётся тем же. Для MVP — оверкилл.

### 6.2. SSR с «оживлением» (Next.js/Nuxt)

- Серверный рендеринг (как сейчас), но на JS. Всё преимущество SSR сохраняется, а JS
  добавляет интерактив. Но бэкенд (FastAPI) пришлось бы либо оставить отдельным API,
  либо полностью переписать на Node — потери по языку Python.

### 6.3. Текущий подход — SSR + ванильный JS (выбран)

- Оптимален: 4 страницы, из которых интерактивна только одна (чат). Никаких фреймворков.
- Когда пора мигрировать: когда появятся (а) история чата со списком диалогов,
  (б) streaming-ответы с обновлением UI, (в) сложное состояние и многостраничные формы.
  Тогда разумный шаг — не React, а улучшение текущего SSR (base.html, streaming через SSE,
  аккуратный клиентский код) или переход на HTMX/htmx-like подход (см. §7).

## 7. Рекомендации (по приоритету)

### P0 — критично

1. **Создать `app/static/`** (или убрать `app.mount("/static", ...)`) — иначе приложение
   не запускается. Заодно появится место под свои `.css`/`.js`.
2. **Убрать `innerHTML` в `index.html`** — заменить на `textContent` (см. §5).

### P1 — высоко

3. **Вынести общий каркас в `base.html`**: `<head>`, CDN-подключения, `<style>`, футер —
   с блоками `{% block %}`. Убирает дублирование и упрощает поддержку.
4. **Перейти с Tailwind CDN на собранный CSS**: через Tailwind CLI (достаточно npm-пакета,
   без фреймворков) генерировать `app/static/css/style.css` и подключать его локально.
   Либо зафиксировать версию CDN-скрипта.
5. **Подключить Lucide с фиксированной версией** (`lucide@0.4xx.0` вместо `@latest`).

### P2 — средний приоритет

6. **Таймаут и обработка ошибок на клиенте чата**: `AbortController` для `fetch`, блокировка
   повторной отправки во время запроса, автоскрытие typing-индикатора по таймеру.
7. **HTML-экранирование на сервере не требуется** (шаблоны без данных), но добавить
   передачу `user` в контекст `/chat` (имя/email в шапке) — станет видна ценность Jinja2.
8. **Перенести JS в отдельные файлы** (`app/static/js/chat.js` и т.п.) — проще линчевать,
   тестировать, кэшировать.
9. Указать `lang="ru"` (или «en» осознанно), поправить «мёртвые» ссылки на лендинге.

### Дальний горизонт

10. **Streaming-ответы (SSE)** — типичный следующий шаг чат-интерфейса. Фронтенд:
    `EventSource`/`fetch` с чтением потока вместо единого `response.json()`.
11. **История чата** — появятся страницы/панели списка диалогов; вот тогда вопрос «SPA
    или SSR» снова станет актуальным и будет решаться в пользу улучшенного SSR или HTMX.

## 8. Итоговая оценка фронтенда

| Критерий | Оценка | Комментарий |
|---|---|---|
| Соответствие задаче | ⭐⭐⭐⭐⭐ | SSR/MPA — оптимальный выбор для 4 страниц |
| Читаемость кода | ⭐⭐⭐⭐☆ | Понятно, но JS «в шаблоне» и дублирование CSS |
| Безопасность | ⭐⭐☆☆☆ | Критичный XSS через `innerHTML` |
| Производительность | ⭐⭐⭐☆☆ | CDN-Tailwind тормозит первый экран |
| Поддерживаемость | ⭐⭐⭐☆☆ | Нет `base.html`, нет статических файлов |
| Готовность к развитию | ⭐⭐☆☆☆ | Приложение не стартует без `app/static/` |

**Общий вердикт:** архитектурный выбор правильный и простой; качество исполнения —
уровень аккуратного прототипа. Проблемы концентрируются в трёх местах: отсутствие
`app/static/` (блокер запуска), `innerHTML` (блокер безопасности) и CDN-зависимости
(прототипный режим Tailwind). При их устранении фронтенд станет production-ready без
каких-либо фреймворков. Переход на React/Vue сейчас нецелесообразен.
