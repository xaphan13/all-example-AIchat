## 1. Краткое резюме

Фронтенд проекта **GroqStreamChain** — это минималистичный одностраничный чат-интерфейс из трёх файлов:

| Файл | Роль |
|---|---|
| `templates/index.html` | HTML-разметка страницы (заголовок, контейнер сообщений, поле ввода) |
| `static/css/style.css` | Оформление: чат-пузыри, индикатор набора текста, адаптивность |
| `static/js/main.js` | Вся клиентская логика: WebSocket-клиент, отправка сообщений, стриминг ответов, авто-переподключение |

Стек — **«классика» без сборщиков**: HTML + CSS + vanilla JavaScript (без jQuery, без React, без Vite). Страница отдаётся сервером через **Jinja2**-шаблонизатор (хотя сам шаблон синтаксис Jinja2 не использует), а общение клиента с сервером идёт по **WebSocket** с потоковой (streaming) отдачей ответов от LLM.

Этот проект — отличный пример для изучения, потому что на нём видно, **как работала фронтенд-разработка «по-старому»**, и понятно, какие проблемы решают современные инструменты (React, Vue, Vite).

## 2. Фундамент: из чего вообще состоит любой веб-фронтенд

Любой фронтенд в браузере — это комбинация трёх технологий:

### 2.1. HTML — структура (каркас)

`HTML (HyperText Markup Language)` — язык разметки. Он описывает **что** есть на странице: заголовки, абзацы, кнопки, поля ввода, картинки.

```html
<div class="chat-container">   <!-- контейнер чата -->
  <button id="send-button">Send</button>  <!-- кнопка с id -->
</div>
```

Ключевая особенность HTML: он **статичный**. Он не может сам что-то вычислить или отреагировать на клик. Это просто описание документа.

### 2.2. CSS — внешний вид (одежда)

`CSS (Cascading Style Sheets)` — каскадные таблицы стилей. Описывает **как выглядит** страница: цвета, отступы, шрифты, анимации, расположение элементов (layout).

```css
.send-button {
  background-color: #6e56cf;   /* фиолетовая кнопка */
  border-radius: 20px;         /* скруглённые углы */
  cursor: pointer;
}
```

Термин «каскадные» означает, что стили наследуются и применяются по приоритету: чем специфичнее селектор, тем он важнее.

### 2.3. JavaScript — поведение (мозг)

`JavaScript (JS)` — единственный язык программирования, встроенный в браузеры. Именно он делает страницы «живыми»: реагирует на клики, отправляет запросы, обновляет DOM.

DOM (Document Object Model) — это древовидное представление HTML-страницы, доступное из JS. Изменяя DOM, JS мгновенно перерисовывает страницу.

```js
// Находим элемент по id
const btn = document.getElementById('send-button');
// Вешаем обработчик клика
btn.addEventListener('click', sendMessage);
```

> **Итог:** HTML — структура, CSS — стили, JS — поведение. Это «святая троица» фронтенда, актуальная с 1995 года и до сих пор.

## 3. Два подхода к генерации страниц: SSR и SPA

Здесь проходит главный водораздел в архитектуре фронтенда.

### 3.1. SSR — Server-Side Rendering (рендеринг на сервере)

Страница собирается **на сервере** и приходит в браузер уже готовым HTML.

```
Браузер ──GET /──▶ Сервер
Браузер ◀──HTML── Сервер  (сервер подставил данные в шаблон)
```

**В этом проекте используется именно этот подход.** Сервер FastAPI на GET-запрос `/` отдаёт готовый HTML через Jinja2 (см. раздел 4).

Плюсы SSR:
- быстрое первое отображение;
- хорошо для SEO (поисковики видят готовый контент);
- просто.

Минусы SSR:
- при каждом переходе страница перезагружается целиком;
- живое взаимодействие (обновление части страницы) требует либо full-reload, либо JS-дополнений.

### 3.2. SPA — Single Page Application (одностраничное приложение)

Браузер один раз получает HTML-«оболочку» и JS-бандл. Дальше вся страница перерисовывается **на клиенте** JS-кодом без перезагрузок. Сервер отдаёт только данные (обычно JSON).

```
Браузер ──GET /──▶ Сервер (один раз: оболочка + JS)
Браузер ◀──JSON── Сервер (далее только данные по API)
```

Так работают React, Vue, Angular-приложения.

Плюсы SPA:
- мгновенный переход между экранами, интерфейс уровня «десктоп-приложения»;
- сервер разгружен от рендеринга HTML.

Минусы SPA:
- дольше первая загрузка (нужно скачать и выполнить JS);
- сложнее SEO (нужен SSR/SSG в дополнение);
- больше кода и инструментов.

> **Нюанс:** у проекта GroqStreamChain фактически **гибрид**. Страница отдаётся через SSR (Jinja2), но все динамические обновления чата делаются на клиенте через WebSocket и JS — как в SPA, но вручную, без фреймворка.

## 4. Jinja2 — шаблонизатор (что он делает в этом проекте)

### 4.1. Что такое шаблонизатор вообще

Шаблонизатор — это инструмент, который подставляет данные в «заготовку» (шаблон) и выдаёт готовый текст. Это похоже на шаблоны в Word: есть каркас документа, а в места `{{ имя }}` подставляются реальные значения.

В мире Python самый известный шаблонизатор — **Jinja2** (используется в Django, Flask, FastAPI). Он вдохновлён шаблонами Django и языком шаблонов Jinja (откуда и название).

### 4.2. Синтаксис Jinja2

```jinja
<!-- Подстановка значения -->
<h1>{{ page_title }}</h1>

<!-- Условие -->
{% if user %}
  <p>Привет, {{ user.name }}!</p>
{% else %}
  <p>Вы не авторизованы</p>
{% endif %}

<!-- Цикл -->
{% for message in messages %}
  <div class="message">{{ message.content }}</div>
{% endfor %}
```

Три базовые конструкции:
- `{{ ... }}` — вывести значение (переменную или выражение);
- `{% ... %}` — выполнить логику (if, for, include, extends);
- `{# ... #}` — комментарий (не попадёт в итоговый HTML).

### 4.3. Как Jinja2 используется в GroqStreamChain

В `server.py`:

```python
from fastapi.templating import Jinja2Templates
templates = Jinja2Templates(directory="templates")

@app.get("/", response_class=HTMLResponse)
async def get_index(request: Request):
    return templates.TemplateResponse("index.html", {"request": request})
```

А в `templates/index.html` — **ни одного Jinja2-тега**. Шаблон полностью статичный: сервер просто отдаёт файл как есть. То есть технически страницу можно было бы раздать как обычный статический файл, а Jinja2 здесь «на будущее» или по инерции типового паттерна FastAPI.

**Это наблюдение важно для отчёта:** подключение шаблонизатора оправданно, когда нужно вставлять в HTML серверные данные (например, первую страницу чата, версию приложения, данные пользователя). Пока таких данных нет — рендер через Jinja2 не даёт выигрыша, но и не вредит.

### 4.4. Какие ещё бывают шаблонизаторы

| Экосистема | Шаблонизатор |
|---|---|
| Python | Jinja2, Django Templates, Mako, Chameleon |
| JavaScript (сервер) | EJS, Handlebars, Pug, Nunjucks |
| .NET | Razor |
| Java | Thymeleaf, FreeMarker, JSP |
| Ruby | ERB, Slim, Haml |

### 4.5. В чём разница между «шаблонизатором» и «фреймворком» (React/Vue)

Важно не путать два уровня:

- **Шаблонизатор (Jinja2)** — превращает шаблон + данные в готовый HTML **на сервере**, один раз, до отправки браузеру.
- **JS-фреймворк (React/Vue)** — строит UI **в браузере**, динамически, и сам управляет его обновлениями при изменении состояния.

Если у вас на странице много интерактива (чат, дашборды, редакторы) — нужен JS-фреймворк. Если страницы в основном статичные (статьи, лендинги) — хватает SSR с шаблонизатором.

## 5. WebSocket — ключевая технология проекта

### 5.1. HTTP vs WebSocket

**HTTP** — запрос-ответный протокол: клиент спрашивает, сервер отвечает, соединение закрывается. Идеален для чтения страниц.

**WebSocket** — протокол для **двусторонней связи в реальном времени** поверх одного постоянного TCP-соединения:

```
Клиент ──── открывает соединение ────▶ Сервер
Клиент ◀─── сервер может слать данные в любой момент ──── Сервер
Клиент ──── и клиент тоже ────▶ Сервер
```

Примеры использования: чаты, онлайн-игры, биржевые котировки, коллаборативные редакторы (Google Docs).

### 5.2. Как происходит рукопожатие

1. Клиент отправляет HTTP-запрос с заголовком `Upgrade: websocket`.
2. Сервер отвечает `101 Switching Protocols`.
3. Дальше соединение работает как WebSocket (схема `ws://` или зашифрованный `wss://`).

### 5.3. WebSocket в GroqStreamChain

- Серверная часть: эндпоинт `@app.websocket("/ws/chat")` в `server.py` (стр. 65–140). На каждое соединение сервер создаёт `session_id`, сохраняет сессию и ждёт сообщения в бесконечном цикле.
- Клиентская часть: `static/js/main.js` создаёт сокет так:

```js
const protocol = window.location.protocol === 'https:' ? 'wss:' : 'ws:';
const wsUrl = `${protocol}//${window.location.host}/ws/chat`;
socket = new WebSocket(wsUrl);
```

Протокол выбирается автоматически: на `http://` → `ws://`, на `https://` → `wss://` (защищённый). Это правильный приём, он позволяет ходить за HTTPS-прокси без правки кода.

- Формат сообщений — JSON с полем `type`, по которому клиент понимает, что делать:

| Тип сообщения (сервер → клиент) | Назначение |
|---|---|
| `session_id` | Сервер присвоил сессии уникальный id |
| `initial_message` | Приветственное сообщение от ассистента |
| `message_received` | Подтверждение: запрос принят, идёт обработка |
| `stream` | Очередной чанк (фрагмент) ответа LLM |
| `stream_end` | Стрим завершён, ввод снова доступен |
| `error` | Ошибка обработки |

### 5.4. Зачем WebSocket для AI-чата

LLM отвечает не мгновенно (секунды). Три варианта UX:

1. **Polling (опрос)** — клиент дёргает сервер каждые N секунд. Медленно и расточительно.
2. **Один большой ответ** — пользователь смотрит на «спиннер» 5–10 секунд, потом всё сразу. Теряет ощущение живости.
3. **Streaming по WebSocket** — сервер передаёт текст **по мере генерации**, слово за словом, как в ChatGPT. Пользователь начинает читать почти сразу.

Проект использует вариант 3 — правильный для современного AI-интерфейса.

## 6. Разбор файлов фронтенда проекта

### 6.1. `templates/index.html` — разметка страницы

Структура (стр. 1–27):

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>GroqStreamChain Chat</title>
  <link rel="stylesheet" href="/static/css/style.css">
</head>
<body>
  <div class="chat-container">
    <header>
      <h1>Let's Chat with GroqStreamChain &#129302;&#128172;</h1>
      <div id="connection-status">Connecting...</div>
    </header>
    <div id="chat-messages" class="messages-container"></div>
    <div class="input-container">
      <textarea id="message-input" placeholder="Type your message here..." rows="3"></textarea>
      <button id="send-button">Send</button>
    </div>
  </div>
  <script src="/static/js/main.js"></script>
</body>
</html>
```

Разбор по элементам:

- `<meta charset="UTF-8">` — кодировка, обязательна для корректного отображения кириллицы.
- `<meta name="viewport">` — настройка масштабирования для мобильных устройств.
- `#connection-status` — индикатор состояния соединения (Connecting / Connected / Disconnected).
- `#chat-messages` — контейнер, куда JS будет добавлять сообщения. Изначально пуст.
- `#message-input` — многострочное поле ввода (`textarea`).
- `#send-button` — кнопка отправки.
- `<script src="/static/js/main.js"></script>` — подключение JS **в конце body**: к этому моменту DOM уже построен, и скрипт гарантированно найдёт свои элементы.

Замечания:
- `lang="en"` — язык страницы английский, хотя текст кнопок и плейсхолдеров тоже английский. Ок, но если интерфейс будет локализован — не забыть поменять.
- Статические ресурсы подключаются по абсолютным путям `/static/...` — благодаря `app.mount("/static", ...)` в `server.py`.

### 6.2. `static/css/style.css` — стили

Что реализовано:

- **Сброс (reset):** `* { margin: 0; padding: 0; box-sizing: border-box; }` — убирает дефолтные отступы и меняет модель размеров (padding больше не увеличивает элемент). Стандартная практика.
- **Центрирование по центру экрана:** флекс-контейнер на `body` + `justify-content/align-items: center`.
- **Карточка чата:** белая, с тенью, скруглениями, фиксированной высотой `90vh` (90% высоты окна).
- **Раскладка:** `.chat-container` — flex-колонка: шапка / список сообщений (растягивается, `flex: 1`) / панель ввода.
- **Пузыри сообщений:** `.user-message` (свой, фиолетовый, справа) и `.assistant-message` (чужой, серый, слева), с «хвостиком» через скругление одного угла (`border-bottom-right-radius: 4px`).
- **Typing indicator:** три точки с CSS-анимацией `@keyframes typing-dot` и задержками `animation-delay` — классическая имитация «печатает…».
- **Code block:** стилизация блоков кода, которые подставляет JS.

Оценка: стили чистые, семантичные, используют современные возможности (flexbox, custom properties нет, но и не нужны при таком объёме). Мобильная версия ограничена `width: 90%` + `max-width: 800px` — на узких экранах это работает приемлемо, но явных `@media`-правил нет.

### 6.3. `static/js/main.js` — клиентская логика (240 строк)

Весь код обёрнут в `document.addEventListener('DOMContentLoaded', ...)` — выполняется после построения DOM.

#### Состояние (стр. 8–14)

```js
let socket = null;                        // WebSocket-соединение
let sessionId = null;                     // id сессии от сервера
let isProcessing = false;                 // идёт ли генерация ответа
let currentAssistantMessageElement = null; // элемент текущего ответа ассистента
let reconnectAttempts = 0;                // счётчик попыток переподключения
const maxReconnectAttempts = 5;
```

#### Подключение и автопереподключение (стр. 17–72)

`connectWebSocket()` — создаёт соединение и вешает обработчики:

- `onopen` — включить кнопку, показать статус Connected, сбросить счётчик попыток.
- `onclose` — выключить кнопку, показать Disconnected и **переподключиться с экспоненциальной задержкой**:

```js
if (reconnectAttempts < maxReconnectAttempts) {
  reconnectAttempts++;
  const delay = Math.min(1000 * Math.pow(2, reconnectAttempts), 10000);
  setTimeout(connectWebSocket, delay);   // 2s, 4s, 8s, 10s, 10s
}
```

Задержки: 2 → 4 → 8 → 10 → 10 секунд. Это называется **exponential backoff** — стандартный механизм устойчивости сетевых клиентов. Реализация корректная.

- `onmessage` — парсит JSON и передаёт в `handleSocketMessage(data)`.
- `onerror` — логирует в консоль (без user-facing сообщения).

#### Обработка сообщений сервера (стр. 75–125)

`switch (data.type)` — диспетчер по типу сообщения:

- `session_id` → сохранить id в `localStorage` (чтобы пережил перезагрузку страницы; правда, дальше этот id не используется — см. замечания).
- `initial_message` → отрендерить приветствие ассистента.
- `message_received` → показать typing-индикатор.
- `stream` → если элемента ответа ещё нет — создать; дописать чанк в него.
- `stream_end` → `isProcessing = false`, снять блокировку ввода.
- `error` → убрать индикатор, показать красное сообщение, разблокировать ввод.

#### Рендеринг сообщений (стр. 127–157)

```js
function createMessageElement(content, role) {
  const messageElement = document.createElement('div');
  messageElement.classList.add('message', `${role}-message`);
  content = processCodeBlocks(content);
  messageElement.innerHTML = content;   // ⚠ см. раздел «Проблемы»
  return messageElement;
}
```

`processCodeBlocks()` — «самодельный мини-markdown»: превращает ```...``` в блоки с классом `.code-block` через регулярное выражение.

`appendToAssistantMessage()` — дописывает чанк к текущему ответу, каждый раз **пересобирая весь innerHTML** текущего сообщения и заново прогоняя через `processCodeBlocks`. Работает, но неоптимально (см. раздел 9).

#### Отправка сообщений (стр. 186–213)

```js
function sendMessage() {
  const message = messageInput.value.trim();
  if (message && !isProcessing && socket && socket.readyState === WebSocket.OPEN) {
    // 1. показать сообщение пользователя в UI
    // 2. очистить поле, заблокировать ввод
    socket.send(JSON.stringify({ message }));  // 3. отправить
    isProcessing = true;
  }
}
```

Защита от «двойной отправки» (проверка `isProcessing` и `readyState`) на месте. Отправка по Enter с `!e.shiftKey` — Enter шлёт, Shift+Enter — перенос строки. Классика чатов.

## 7. Общая картина: поток данных во фронтенде проекта

```
1. Браузер запрашивает http://localhost:8000/
2. FastAPI рендерит templates/index.html (Jinja2) → готовый HTML
3. Браузер грузит /static/css/style.css и /static/js/main.js
4. main.js открывает WebSocket ws://localhost:8000/ws/chat
5. Сервер шлёт: {"type":"session_id", ...} и {"type":"initial_message", ...}
6. Клиент рендерит приветствие, статус "Connected"
7. Пользователь пишет сообщение → Enter → socket.send(JSON.stringify({message}))
8. Сервер шлёт {"type":"message_received"} → клиент показывает "печатает…"
9. Сервер стримит {"type":"stream","content":"..."} по кусочкам
10. Клиент дописывает каждый чанк в пузырь ассистента (перерисовка innerHTML)
11. Сервер шлёт {"type":"stream_end"} → клиент снимает блокировку ввода
12. При обрыве связи → авто-переподключение с нарастающей задержкой
```

Ключевое свойство этого фронтенда: **вся логика — императивная и процедурная**. Разработчик вручную управляет DOM: `createElement`, `appendChild`, `innerHTML`. В современном фронтенде это делает фреймворк.

## 8. Современный фронтенд: React, Vue, Vite и всё остальное

Теперь — расширенная часть. Это «большой экскурс», зачем вообще существуют эти инструменты.

### 8.1. Проблема, которую решают фреймворки

Когда страница становится сложной (много элементов, данных, состояний), «ручное» управление DOM превращается в кошмар:

```js
// Типичный ад императивного подхода:
// надо не забыть: обновить элемент, пересчитать размер, обновить счётчик,
// скрыть спиннер, сохранить состояние...
```

Ошибки легко порождают рассинхрон: **состояние в JS-переменных** и **картинка на экране** живут отдельно и расходятся.

Фреймворки решают это главной идеей: **«UI — это функция от состояния»** (UI = f(state)). Изменилось состояние — фреймворк сам перерисовал нужную часть экрана. Программист больше не трогает DOM руками.

### 8.2. React

Создан в 2013 году в Facebook (Meta). Сейчас — самый популярный фреймворк в мире.

Основные понятия:
- **Компоненты** — функции/классы, возвращающие разметку. Компоненты можно переиспользовать и вкладывать друг в друга.
- **JSX** — синтаксис, позволяющий писать HTML прямо в JavaScript:

```jsx
function Message({ role, content }) {
  return (
    <div className={`message ${role}-message`}>
      {content}
    </div>
  );
}
```

- **Props** — данные, передаваемые сверху вниз в компоненты.
- **State** — внутреннее состояние компонента; при его изменении React перерисовывает компонент.
- **Virtual DOM** — виртуальное «зеркало» страницы; React сравнивает старое и новое состояние виртуального дерева (diffing) и применяет к реальному DOM только изменения. Это делает перерисовку быстрой.
- **Hooks** (`useState`, `useEffect`) — функции для работы с состоянием и жизненным циклом в функциональных компонентах.

Как тот же чат выглядел бы на React:

```jsx
function Chat() {
  const [messages, setMessages] = useState([]);
  const [input, setInput] = useState('');

  const onStream = (chunk) => {
    // React сам обновит только нужные узлы DOM
    setMessages(prev => [...prev, chunk]);
  };

  return <MessageList messages={messages} />;
}
```

**Экосистема React:** Redux/Zustand (управление состоянием), React Router (навигация), Next.js (SSR-фреймворк поверх React), React Native (мобильная разработка).

### 8.3. Vue

Создан в 2014 году Эваном Ю. Средний путь между «просто» и «мощно». Часто хвалят за низкий порог входа.

- **Template + Options/Composition API.** Vue использует HTML-подобные шаблоны с директивами:

```vue
<template>
  <div class="message" :class="role">
    {{ content }}
  </div>
</template>

<script setup>
import { ref } from 'vue';
const content = ref('Привет!');
</script>
```

- **Реактивность** — Vue автоматически отслеживает зависимости и перерисовывает только то, что изменилось (более «тонкий» механизм, чем Virtual DOM React; в Vue 3 используется Proxy-основа).
- **Single-File Components (SFC)** — один `.vue`-файл содержит шаблон, скрипт и стили компонента.

**Экосистема Vue:** Pinia (состояние), Vue Router (навигация), Nuxt (SSR-фреймворк), Quasar/Vuetify (UI-библиотеки).

### 8.4. Svelte и Solid (альтернативные подходы)

- **Svelte** — «компилятор, а не фреймворк». Ваш код компилируется в чистый JS **без** runtime-библиотеки в браузере. Страница получается маленькая и быстрая. Нет Virtual DOM вообще.
- **Solid** — использует сигналы (signals) для реактивности, перерисовывает точечно, часто считается «самым быстрым» из популярных.

### 8.5. Фреймворк vs библиотека

- **React/Vue** часто называют фреймворками, хотя React технически библиотека (он не диктует структуру приложения).
- Настоящие фреймворки (Angular, Next.js, Nuxt) дают целостное решение: роутинг, сборку, серверную часть, паттерны.

### 8.6. Angular

Полноценный корпоративный фреймворк от Google (TypeScript, DI-контейнер, RxJS, модули). Мощный, но тяжёлый и с высокой кривой обучения. Для проектов уровня GroqStreamChain избыточен.

### 8.7. Vite — сборщик и дев-сервер

**Vite** (2019, автор Эван Ю) — это **сборочный инструмент**, не фреймворк. Он отвечает за:

1. **Dev-сервер** с горячей перезагрузкой (HMR): меняете файл — браузер мгновенно обновляет страницу без полной перезагрузки.
2. **Сборку (build)** — объединяет десятки/сотни JS/CSS-файлов в оптимизированные бандлы для production, минифицирует, добавляет хэши в имена файлов (кэш-басты), обрабатывает изображения, транспилирует современный JS для старых браузеров.

Почему Vite быстрый: он отдаёт в dev **нативные ES-модули браузера** (`import`/`export`) без предварительной «упаковки» всех файлов. Устаревший предшественник **Webpack** собирал проект целиком при каждом изменении — на больших проектах это секунды и десятки секунд. Vite собирает только изменённый файл → миллисекунды.

```
Vite (вместе с React/Vue) — стандартный набор:
  npm create vite@latest my-app -- --template react
  npm run dev      → дев-сервер с HMR
  npm run build    → production-бандл в dist/
```

**Другие сборщики:** Webpack (король 2015–2021), Rollup (лежит в основе Vite), esbuild (молниеносная транспиляция, тоже внутри Vite), Parcel, Turbopack.

### 8.8. TypeScript

Строгая типизация поверх JavaScript. Даёт автодополнение, ловит ошибки до запуска. Современный стандарт фронтенда (даже GitHub советует всем новым проектам). Помимо фронтенда используется в Node.js.

### 8.9. CSS-инструменты

- **CSS Modules / CSS-in-JS** (styled-components, Emotion) — изоляция стилей по компонентам.
- **Препроцессоры** SCSS/Sass, Less — переменные, вложенность, миксины (их нет в чистом CSS).
- **Tailwind CSS** — «utility-first»: готовые классы в HTML, без отдельных CSS-файлов.
- **PostCSS** — плагинная обработка CSS.

## 9. Сильные и слабые стороны фронтенда проекта

### Сильные стороны

1. **Простота и прозрачность.** Ноль зависимостей на клиенте. Любой JS-разработчик понимает `main.js` за минуты.
2. **Стриминг-рендеринг.** Ответы LLM появляются «на лету» — современный UX.
3. **Авто-переподключение** с exponential backoff — надёжность «из коробки».
4. **Защита от повторной отправки** (`isProcessing`, `readyState` check).
5. **Отделение кода от разметки** — HTML/CSS/JS разделены по стандартной схеме FastAPI (`templates/` + `static/`).
6. **Аккуратный CSS** — флекс-раскладка, плавные переходы, индикатор печати.

### Слабые стороны и проблемы

#### P0 — критичные

| # | Проблема | Где | Почему плохо |
|---|---|---|---|
| 1 | **XSS-уязвимость** — контент от LLM/пользователя вставляется через `innerHTML` | `main.js:135`, `main.js:151–154` | Модель может сгенерировать `<script>` или событийные атрибуты (например, `<img onerror="...">`), и код выполнится в браузере пользователя. **Исправление:** использовать `textContent`, либо `DOMPurify.sanitize()` перед вставкой, либо безопасный markdown-рендерер (`marked` + sanitizer). |
| 2 | **Пересборка innerHTML на каждый чанк** | `appendToAssistantMessage()` | Каждый чанк заново парсит и перерисовывает весь ответ. При длинных ответах — деградация производительности, мигание, потеря фокуса выделения текста. **Исправление:** добавлять текст через `document.createTextNode` + инкрементальный рендер. |

#### P1 — важные

| # | Проблема | Где | Комментарий |
|---|---|---|---|
| 3 | `sessionId` сохраняется в `localStorage`, но **нигде не используется** | `main.js:80` | Клиент шлёт только `{message}` без `session_id`; сервер игнорирует сохранённый id и создаёт новую сессию на каждое соединение. Мёртвый код / недоделанная фича «восстановления истории». |
| 4 | Нет обработки ошибок WebSocket на уровне UX | `onerror` → только `console.error` | Пользователь не видит причину обрыва. |
| 5 | Нет рендера markdown (кроме блоков кода) | `processCodeBlocks()` | Жирный, списки, ссылки приходят как сырой текст. Для AI-чата markdown — де-факто стандарт (стоит взять `marked`/`marked-it` + `DOMPurify`). |
| 6 | `main.js` — монолит из 240 строк | весь файл | Нет модульности; тестировать нельзя без DOM-окружения. Можно разбить на модули (ES modules) без сборщика: `ws-client.js`, `ui.js`, `chat.js`. |
| 7 | Скролл вниз каждый чанк | `messagesContainer.scrollTop = scrollHeight` | Хорошо в начале ответа, но при чтении пользователем истории — дёргает. Правильно: автопрокрутка только если пользователь и так внизу. |

#### P2 — мелочи

- Нет favicon, нет `<meta description>`, нет `aria-label` для интерактивных элементов (доступность).
- Отсутствие `@media`-правил для мобильных (работает за счёт гибких процентов, но без явной адаптации).
- При `stream_end` не выводится ничего, если стрим был пустым.
- Эмодзи в заголовке закодированы HTML-сущностями — корректно, но нечитаемо.

## 10. Как бы выглядел этот фронтенд на современном стеке

### Вариант A — «осовременить без фреймворка» (рекомендуется для такого объёма)

Оставить vanilla JS, но навести порядок:

1. Заменить `innerHTML` → `textContent` + `DOMPurify` для markdown.
2. Разбить `main.js` на ES-модули (`import`/`export`), подключить `<script type="module">`.
3. Использовать `marked` + `DOMPurify` для полноценного markdown.
4. Прогрессивный рендер: текст — через `textContent`, без пересборки.
5. Добавить адаптивность и доступность.

Никаких сборщиков не нужно — современные браузеры понимают ES-модули нативно.

### Вариант B — React + Vite (стандарт индустрии)

Архитектура почти не изменилась бы концептуально:

```
src/
├── main.tsx                 # входная точка, монтирование React
├── App.tsx                  # корневой компонент
├── components/
│   ├── ChatContainer.tsx    # контейнер чата
│   ├── MessageList.tsx      # список сообщений (виртуализация при длине)
│   ├── MessageBubble.tsx    # один пузырь
│   ├── MessageInput.tsx     # поле ввода + кнопка
│   └── TypingIndicator.tsx  # индикатор печати
├── hooks/
│   └── useChatSocket.ts     # обёртка над WebSocket (useState + useEffect)
├── lib/
│   └── markdown.ts          # safe markdown render
└── styles/
    └── chat.css
```

Выгода: декларативный рендер (пришёл чанк — React сам перерисует), компонентность, HMR от Vite в разработке, TypeScript, тесты с Vitest + Testing Library. Сборка `vite build` отдаст оптимизированный бандл.

Цена: node_modules, новая архитектура, больше инструментов — оправдано, если проект будет расти (авторизация, истории чатов, несколько страниц).

### Вариант C — Vue + Vite

Тот же результат с чуть более «лёгким» порогом входа; `.vue`-файлы объединяют шаблон/скрипт/стили.

### Какую роль играл бы Jinja2 в этих вариантах

В SPA-варианте Jinja2 уже не нужен: сервер отдаёт статический бандл (или, при желании, оболочку страницы с метаданными), а всё содержимое рендерит JS.

| Критерий | Текущий проект (HTML+JS+Jinja2) | React/Vue + Vite |
|---|---|---|
| Зависимости клиента | 0 | десятки (в бандле) |

| Тестируемость | низкая | высокая (Vitest/Testing Library) |
| Типизация | нет | TypeScript |
| Инструменты разработки | текстовый редактор | Vite dev-server с HMR, ESLint, Prettier |
| Для чего подходит | прототипы, лендинги, небольшие виджеты | сложные интерактивные приложения |

## 12. Словарик терминов (шпаргалка)

| Термин | Определение |
|---|---|
| **HTML** | Язык разметки, описывает структуру страницы |
| **CSS** | Каскадные стили, описывают внешний вид |
| **JavaScript** | Язык программирования в браузере, оживляет страницы |
| **DOM** | Древовидное представление страницы, с которым работает JS |
| **SSR** | Серверный рендеринг: HTML собирается на сервере |
| **SPA** | Одностраничное приложение: HTML/JS один раз, дальше рендер на клиенте |
| **SSG** | Static Site Generation: HTML собирается заранее при сборке |
| **Jinja2** | Python-шаблонизатор: `{{ }}`, `{% %}`, `{# #}` |
| **WebSocket** | Постоянное двустороннее соединение для real-time (чат, стриминг) |
| **Streaming** | Постепенная передача данных (текст LLM по чанкам) |
| **Компонент** | Переиспользуемый «кирпичик» UI (функция, возвращающая разметку) |
| **State** | Состояние приложения; изменение state → перерисовка UI |
| **Props** | Данные, передаваемые в компонент сверху |
| **Virtual DOM** | Виртуальное дерево для эффективного обновления реального DOM |
| **JSX** | Синтаксис HTML-в-JS для React |
| **Hooks** | Функции React для состояния и эффектов (`useState`, `useEffect`) |
| **Vite** | Сборщик + дев-сервер с мгновенным HMR |
| **Webpack** | Классический сборщик (устаревает, но широко распространён) |
| **HMR** | Hot Module Replacement — мгновенное обновление модуля в браузере без перезагрузки |
| **Бандл** | Один (или несколько) итоговых JS/CSS-файлов после сборки |
| **TypeScript** | Надмножество JS со статической типизацией |

| **XSS** | Уязвимость: выполнение произвольного кода через вставку непроверенного HTML |
| **Exponential backoff** | Повторные попытки с растущей задержкой (2s→4s→8s…) |

## 13. Выводы

1. **Фронтенд GroqStreamChain выполнен качественно для своего масштаба**: простой, читаемый, без лишних зависимостей, с корректным стримингом и авто-переподключением.
2. **Главные технические долги** — XSS через `innerHTML` (чинится в 10 строк через `DOMPurify`/`textContent`) и пересборка DOM на каждый чанк.
3. **Jinja2 здесь используется «вхолостую»** — шаблон статичный. Это не ошибка, а задел: при появлении серверных данных (имя пользователя, список сессий) шаблонизатор станет полезным.
4. **Переходить на React/Vue прямо сейчас смысла нет** — объём интерфейса мал. Но если проект будет расти (многостраничность, авторизация, история чатов, markdown-редактор), разумно переехать на React/Vue + Vite, сохранив WebSocket-протокол без изменений — серверная часть от этого не зависит.
5. **Протокол WebSocket — самая ценная часть архитектуры**, и её можно не менять ни при каком рефакторинге фронтенда: типы сообщений (`session_id`, `stream`, `stream_end`, `error`) спроектированы аккуратно и покрывают все нужные состояния.
