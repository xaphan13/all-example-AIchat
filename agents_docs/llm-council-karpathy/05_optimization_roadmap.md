# 05 — Предложения по развитию (Optimization Roadmap)

> Приоритеты: P0 — корректность/безопасность, P1 — производительность и надёжность, P2 — DX и расширяемость.

## 1. Архитектурные улучшения

### P0 — Устранить риск потери данных
- **Атомарные записи** в `backend/storage.py`: писать во временный файл (`*.tmp`) + `os.replace()`; при ошибке старый файл остаётся нетронутым.
- **Идемпотентность сообщений**: принимать опциональный `client_message_id` (UUID) в `SendMessageRequest`, дедуплицировать при записи в `add_user_message()`.
- **Незавершённые диалоги**: при клиентском обрыве SSE завершать транзакцию — либо фиксировать «битое» сообщение с флагом `status: "interrupted"`, либо откатывать user-сообщение (сейчас остаётся «сообщение без ответа»).
- **Блокировка на диалог**: `asyncio.Lock` (в памяти) или flock на файл — исключить гонку read-modify-write при параллельных запросах на один диалог.

### P1 — Вынести асинхронную работу из HTTP-слоя
Сейчас три стадии выполняются внутри HTTP-запроса (SSE-генератор): при падении воркера/редистрибуции всё теряется. Варианты:
- **Worker + очередь** (minimal): бэкенд-задача в `asyncio.Queue` + отдельный worker; HTTP возвращает `job_id`, SSE подписывается на `job_id`. Дешевле, чем полноценный брокер.
- **Брокер сообщений** (RabbitMQ/Redis Streams) — только если ожидается реальная многопользовательская нагрузка; для локального прототипа избыточно.
- Альтернатива без очередей: **двухфазное сохранение** — писать каждый завершённый этап (stage1/stage2/stage3) в файл отдельными событиями и при ретрае достраивать незавершённый диалог.

### P1 — Разделить «совет» и «транспорт»
Выделить слой сервисов с Pydantic-DTO (`Stage1Result`, `Stage2Result`, `Stage3Result`, `CouncilMetadata`) вместо `List[Dict[str, Any]]`, а в `backend/main.py` оставить только адаптацию HTTP↔сервис. Это убирает дублирование между `/message` и `/message/stream`, делает бизнес-логику тестируемой без сети.

### P2 — Конфигурируемость вместо хардкода
- Модели, председатель, модель заголовков и таймауты — из переменных окружения с дефолтами из `backend/config.py` (`COUNCIL_MODELS=...`, `CHAIRMAN_MODEL=...`, `TITLE_MODEL=...`, `MODEL_TIMEOUT=...`).
- Вынести `google/gemini-2.5-flash` из `council.py` в конфиг.
- Фронтенд: `VITE_API_BASE` через `import.meta.env` вместо захардкоженного `http://localhost:8001` в `frontend/src/api.js`.
- Добавить `.env.example` (сейчас его нет — легко пропустить обязательный ключ).

### P2 — Мультитурн и персистентность метаданных
- Снять ограничение single-turn в `ChatInterface.jsx` (поле ввода при `messages.length > 0`), либо явно зафиксировать single-turn в README.
- Персистить `label_to_model` и `aggregate_rankings` в assistant-сообщение — сейчас после перезагрузки страницы Stage 2 теряет деанонимизацию и «Street Cred».

## 2. Оптимизация производительности

| Участок | Текущее поведение | Рекомендация | Ожидаемый эффект |
|---|---|---|---|
| `query_model()` — новый `httpx.AsyncClient` на каждый вызов | TLS-handshake + новый connection pool на 4+ запросов на стадию | Единый клиент в `lifespan`/`app.state` (или `httpx.AsyncClient(timeout=…)` уровня модуля) | −10…30% накладных расходов на стадию; снижение нагрузки на сеть |
| `query_models_parallel()` — `asyncio.gather` без `return_exceptions` | неявно «безопасен» только из-за внутреннего `try/except` | `return_exceptions=True` + классификация ошибок (timeout vs 4xx vs 5xx) | Диагностируемость; готовность к ретраям |
| Отсутствие retry/backoff | 1 попытка, таймаут 120 c | Ретраи 3× с экспоненциальным backoff и учётом HTTP-заголовков OpenRouter (`Retry-After`, `X-RateLimit-*`); для нестабильных моделей — свой таймаут | Заметно меньше «выпавших» моделей из стадий |
| `parse_ranking_from_text()` вызывается дважды | в `stage2_collect_rankings` и повторно в `calculate_aggregate_rankings` | Передавать готовый `parsed_ranking` в агрегатор | Микро-ускорение; устранение дублирования |
| `storage.list_conversations()` читает все файлы целиком | O(n) полных чтений/парсингов JSON на каждый заход в сайдбар | Кэш-индекс `{id: metadata}` в памяти (инвалидация при записи) или отдельный метаданный файл; при росте — SQLite | Сильный выигрыш при 100+ диалогах |
| Стриминг LLM-ответов | каждая модель отдаёт полный текст за один вызов | `"stream": true` в payload + частичные SSE-события из `openrouter.py` (потребует маршрутизации стримов в общий SSE) | Уменьшение TTFB в разы; прогресс-бар по стадиям |
| Стадии последовательны | stage2 ждёт все ответы stage1 | Частичный конвейер: ранжировать ответы по мере готовности (spawn asyncio-задач), председателю отдавать уже готовые рецензии | Экономия в среднем ~1/2 времени самой медленной модели |
| Генерация заголовка | отдельный LLM-вызов | Параллелить со Stage 1 (в стриминге уже так), в не-стриминге убрать ожидание; либо хеш-эвристика на основе первых слов вопроса | −3…10 c на первый вопрос в не-стриминговом пути |

## 3. Рефакторинг: первоочередные файлы

### `backend/main.py` — первым
**Почему**: единственный файл с реальным дублированием логики (`send_message` / `send_message_stream`), хрупкой обработкой задач и отсутствием валидации.
**Что сделать**: выделить общий `_process_message(conversation_id, content, *, stream)` (или сервис `CouncilService`); вынести таймауты/лимиты в конфиг; добавить `len(content)`-лимит и проверку непустоты; закрывать `title_task` при обрыве (`finally: task.cancel()`).

### `backend/storage.py` — второй
**Почему**: риск повреждения данных (неатомарность), гонки, path traversal.
**Что сделать**: `os.replace` + временные файлы; валидация `conversation_id` по regex `[0-9a-f-]{36}`; `datetime.now(timezone.utc)` вместо `utcnow()`; опциональный слой блокировок.

### `backend/council.py` — третий
**Почему**: `calculate_aggregate_rankings` пересчитывает парсинг; хардкод title-модели; промпты и парсер — идеальные кандидаты для юнит-тестов.
**Что сделать**: передавать `parsed_ranking` в агрегатор; константы промптов вынести в отдельный модуль (`backend/prompts.py`); модель заголовков — в `config.py`; разбить `run_full_council` на явный `CouncilPipeline` с шагами.

### `frontend/src/App.jsx` — четвёртый
**Почему**: мутация объектов в state — источник трудновоспроизводимых багов рендера; вся обработка SSE в одном обработчике.
**Что сделать**: функциональные обновления через `map` без мутаций; вынести обработку событий в `useReducer`; добавить обработку `error`-события в UI (сейчас — только `console.error` и сброс `isLoading`).

### `frontend/src/api.js` — пятый
**Почему**: хрупкий SSE-парсер.
**Что сделать**: буферизующий парсер (аккумулировать строку до `\n\n`, поддержка нескольких `data:` строк на событие, `event:`/`id:`), таймаут и `AbortController` для отмены.

## 4. DX: тесты, CI/CD, локальный запуск

### Тесты (сейчас — 0)
- **Юнит** (pytest + pytest-asyncio):
  - `parse_ranking_from_text()` — канонический формат, лишний текст после `FINAL RANKING:`, отсутствие маркера, разные регистры;
  - `calculate_aggregate_rankings()` — пропуск неизвестных меток, пустые рецензии, сортировка;
  - `storage.py` — CRUD-цикл, «не найден диалог», повреждённый JSON, путь с `..` (должен отклоняться).
- **Интеграционные**: воссоздать `test_openrouter.py` из `CLAUDE.md` (проверка подключения к API и тест разных идентификаторов моделей в streaming/non-streaming режимах) — сейчас файла нет, документация устарела; мокировать `httpx` с фикстурами ответов OpenRouter.
- **E2E-минимум**: поднять бэкенд с моками моделей (fake-council для локального dev), прогнать SSE-поток и рендер трёх стадий (Playwright).

### CI/CD
- **GitHub Actions**: job `backend` (ruff check + pytest через `uv`), job `frontend` (`npm ci && npm run lint && npm run build`).
- **Pre-commit**: `ruff` + `eslint` + форматтер (black/ruff-format).
- **Проверка покрытия**: порог на ключевые модули `council.py`, `storage.py`.

### Локальный запуск
- `start.sh` — только bash; добавить `start.ps1` для Windows (или документировать два терминала).
- Dev-режим бэкенда: `uvicorn backend.main:app --reload` (сейчас рестарт вручную при каждой правке).
- `uv run`/`uv sync` уже заданы; добавить в `pyproject.toml` dev-зависимости (`pytest`, `pytest-asyncio`, `httpx`-mock, `ruff`) через опциональную группу `[dependency-groups]`.
- **Fake-council**: скрипт/мод для запуска без `OPENROUTER_API_KEY` — детерминированные фейковые ответы для разработки UI без сжигания токенов.

## Приоритезация (quick wins → долгие работы)

1. **День 1**: валидация `conversation_id` + атомарные записи + непустой `content` (P0-безопасность).
2. **День 1–2**: shared `httpx.AsyncClient`, ретраи, исправление мутации state в `App.jsx`, фикс SSE-парсера.
3. **День 2–3**: юнит-тесты на парсер/агрегатор/хранилище; CI-пайплайн.
4. **Неделя 1–2**: вынос очереди задач, DTO, персистентность метаданных, мультитурн-UI.
5. **Опционально**: стриминг LLM-ответов, SQLite вместо JSON, конфигурируемость моделей через UI (из «Future Enhancement Ideas» в `CLAUDE.md`).
