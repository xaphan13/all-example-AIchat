# CLAUDE.md — Технические заметки по LLM Council

Этот файл содержит технические детали, архитектурные решения и важные заметки по реализации для будущих сессий разработки.

## Обзор проекта

LLM Council — это трёхстадийная система делиберации, в которой несколько LLM совместно отвечают на вопросы пользователя. Ключевая инновация — анонимизированное взаимное рецензирование на Stage 2, предотвращающее предвзятость моделей при оценке.

## Архитектура

### Структура бэкенда (`backend/`)

**`config.py`**
- Содержит `COUNCIL_MODELS` (список идентификаторов моделей OpenRouter)
- Содержит `CHAIRMAN_MODEL` (модель, синтезирующая финальный ответ)
- Использует переменную окружения `OPENROUTER_API_KEY` из `.env`
- Бэкенд работает на **порту 8001** (НЕ 8000 — на 8000 у пользователя было другое приложение)

**`openrouter.py`**
- `query_model()`: Одиночный асинхронный запрос к модели
- `query_models_parallel()`: Параллельные запросы через `asyncio.gather()`
- Возвращает словарь с `content` и опциональным `reasoning_details`
- Мягкая деградация: при неудаче возвращает None и продолжает работу с успешными ответами

**`council.py`** — Основная логика
- `stage1_collect_responses()`: Параллельные запросы ко всем моделям совета
- `stage2_collect_rankings()`:
  - Анонимизирует ответы как «Response A, B, C, и т.д.»
  - Создаёт маппинг `label_to_model` для деанонимизации
  - Просит модели оценить и ранжировать (со строгими требованиями к формату)
  - Возвращает кортеж: (список_ранжирований, словарь_label_to_model)
  - Каждое ранжирование содержит как сырой текст, так и список `parsed_ranking`
- `stage3_synthesize_final()`: Председатель синтезирует ответ из всех ответов + ранжирований
- `parse_ranking_from_text()`: Извлекает секцию «FINAL RANKING:», обрабатывает как нумерованные списки, так и простой формат
- `calculate_aggregate_rankings()`: Вычисляет среднюю позицию ранга по всем взаимным оценкам

**`storage.py`**
- Хранение диалогов в JSON-файлах в `data/conversations/`
- Каждый диалог: `{id, created_at, messages[]}`
- Сообщения ассистента содержат: `{role, stage1, stage2, stage3}`
- Примечание: метаданные (label_to_model, aggregate_rankings) НЕ сохраняются в хранилище, а возвращаются только через API

**`main.py`**
- FastAPI-приложение с включённым CORS для localhost:5173 и localhost:3000
- POST `/api/conversations/{id}/message` возвращает метаданные в дополнение к стадиям
- Метаданные включают: маппинг label_to_model и aggregate_rankings

### Структура фронтенда (`frontend/src/`)

**`App.jsx`**
- Основная оркестрация: управление списком диалогов и текущим диалогом
- Обработка отправки сообщений и хранения метаданных
- Важно: метаданные хранятся в состоянии UI для отображения, но не персистятся в бэкенд-JSON

**`components/ChatInterface.jsx`**
- Многострочное текстовое поле (3 строки, изменяемого размера)
- Enter — отправка, Shift+Enter — новая строка
- Сообщения пользователя обёрнуты в класс markdown-content для отступов

**`components/Stage1.jsx`**
- Таб-просмотр индивидуальных ответов моделей
- Рендеринг через ReactMarkdown с обёрткой markdown-content

**`components/Stage2.jsx`**
- **Критическая функция**: Таб-просмотр «сырого» текста оценки от каждой модели
- Деанонимизация происходит НА КЛИЕНТЕ для отображения (модели получают анонимные метки)
- Под каждой оценкой показывается «Extracted Ranking», чтобы пользователи могли проверить парсинг
- Агрегированные ранжирования показываются со средней позицией и количеством голосов
- Пояснительный текст уточняет, что жирные имена моделей нужны только для читаемости

**`components/Stage3.jsx`**
- Финальный синтезированный ответ председателя
- Зелёный фон (#f0fff0) для выделения итога

**Стили (`*.css`)**
- Светлая тема (не тёмная)
- Основной цвет: #4a90e2 (синий)
- Глобальные стили markdown в `index.css` через класс `.markdown-content`
- Отступ 12px для всего markdown-контента во избежание загромождения

## Ключевые проектные решения

### Формат промпта Stage 2
Промпт Stage 2 очень специфичен для обеспечения парсимого вывода:
```
1. Сначала оценить каждый ответ индивидуально
2. Добавить заголовок «FINAL RANKING:»
3. Нумерованный список в формате: «1. Response C», «2. Response A», и т.д.
4. Без дополнительного текста после секции ранжирования
```
Этот строгий формат позволяет надёжно парсить вывод, получая при этом вдумчивые оценки.

### Стратегия деанонимизации
- Модели получают: «Response A», «Response B» и т.д.
- Бэкенд создаёт маппинг: `{"Response A": "openai/gpt-5.1", ...}`
- Фронтенд отображает имена моделей **жирным** для читаемости
- Пользователи видят пояснение, что оригинальная оценка использовала анонимные метки
- Это предотвращает предвзятость, сохраняя прозрачность

### Философия обработки ошибок
- Продолжать с успешными ответами, если некоторые модели упали (мягкая деградация)
- Никогда не валить весь запрос из-за сбоя одной модели
- Логировать ошибки, но не показывать пользователю, если только не все модели упали

### Прозрачность UI/UX
- Все сырые выводы доступны для просмотра через вкладки
- Распарсенные ранжирования показаны под сырым текстом для валидации
- Пользователи могут проверить интерпретацию системой вывода моделей
- Это формирует доверие и позволяет отлаживать краевые случаи

## Важные детали реализации

### Относительные импорты
Все модули бэкенда используют относительные импорты (например, `from .config import ...`), а не абсолютные. Это критично для корректной работы модульной системы Python при запуске как `python -m backend.main`.

### Конфигурация портов
- Бэкенд: 8001 (изменён с 8000 во избежание конфликта)
- Фронтенд: 5173 (дефолт Vite)
- При изменении обновлять и `backend/main.py`, и `frontend/src/api.js`

### Рендеринг Markdown
Все компоненты ReactMarkdown должны быть обёрнуты в `<div className="markdown-content">` для корректных отступов. Этот класс определён глобально в `index.css`.

### Конфигурация моделей
Модели захардкожены в `backend/config.py`. Председатель может быть тем же или отличаться от членов совета. Текущий дефолт — Gemini в качестве председателя по предпочтению пользователя.

## Частые подводные камни

1. **Ошибки импорта модулей**: Всегда запускать бэкенд как `python -m backend.main` из корня проекта, а не из директории backend
2. **Проблемы CORS**: Фронтенд должен совпадать с разрешёнными источниками в CORS-middleware `main.py`
3. **Сбои парсинга ранжирований**: Если модели не следуют формату, fallback-regex извлекает любые паттерны «Response X» по порядку
4. **Отсутствующие метаданные**: Метаданные эфемерны (не персистятся), доступны только в API-ответах

## Сводка потока данных

```
Запрос пользователя
    ↓
Stage 1: Параллельные запросы → [индивидуальные ответы]
    ↓
Stage 2: Анонимизация → Параллельные запросы ранжирования → [оценки + распарсенные ранжирования]
    ↓
Расчёт агрегированных ранжирований → [сортировка по средней позиции]
    ↓
Stage 3: Синтез председателем с полным контекстом
    ↓
Возврат: {stage1, stage2, stage3, metadata}
    ↓
Фронтенд: Отображение с вкладками + UI валидации
```

Весь поток async/параллельный там, где возможно, для минимизации задержки.
