# 04 — Оценка качества кодовой базы

> Оценка на момент анализа (git HEAD `ecb2f79`, 6 коммитов). Проект позиционируется как «vibe-coded» прототип — общая оценка соответствует уровню прототипа: работает, читается, но не готов к продакшену.

## Читаемость, модульность, связность

### Сильные стороны
- **Малый размер и прозрачность**: ~900 строк кода суммарно; каждый модуль решает одну задачу и читается целиком за один проход.
- **Чёткое разделение слоёв**: `main.py` (HTTP) / `council.py` (бизнес) / `openrouter.py` (интеграция) / `storage.py` (данные). Связность между слоями минимальна и идёт через явные импорты и типизированные сигнатуры.
- **Хорошие docstring'и** на всех публичных функциях бэкенда с описанием параметров и возвращаемых значений.
- **Аннотации типов** (`typing.List/Dict/Tuple/Any`) присутствуют в большинстве публичных сигнатур.
- **Смысловые названия** функций и переменных соответствуют домену («совет», «рецензия», «председатель»).

### Слабые стороны
- **Функциональный стиль вместо объектного**: вся бизнес-логика — модульные функции без классов; это приемлемо, но затрудняет тестирование (нет DI, стабы заменить сложно) и расширение.
- **Утечки абстракции**: `stage2_results` — словари с произвольной структурой; типизация `List[Dict[str, Any]]` не даёт контракта данных. Pydantic-модели используются только для входных/выходных форм API, но не для внутренних DTO.
- **Импорты внутри функций**: `import re` в `parse_ranking_from_text()` (`backend/council.py`), `import asyncio` в `query_models_parallel()` (`backend/openrouter.py`), `from collections import defaultdict` в `calculate_aggregate_rankings()`. Непоследовательно — остальные импорты на уровне модуля.
- **Дублирование логики** между `send_message()` и `send_message_stream()` в `backend/main.py`: оба проверяют существование диалога, добавляют user-сообщение, вызывают стадии и сохраняют результат — общий код не выделен.
- **Устаревшая документация**: `CLAUDE.md` упоминает `test_openrouter.py` и описывает стриминг как «будущую» фичу, хотя стриминг реализован; часть сведений не соответствует коду (см. § Устаревание).

## Соответствие стандартам и идиомам

| Критерий | Оценка | Комментарий |
|---|---|---|
| **DRY** | ⚠️ Удовл. | Повторяющиеся паттерны: сборка контекста стадий, проверка `if response is not None`, дубль логики двух message-роутов, повторный парсинг рейтингов (`council.py` вычисляет `parsed_ranking` в Stage 2, а `calculate_aggregate_rankings` парсит текст заново) |
| **KISS** | ✅ Хорошо | Код прост до предела, без преждевременных абстракций |
| **SOLID** | ⚠️ Частично | S — выполнено; O/C — плохо: добавление новой стадии/модели требует правок в `council.py` и `config.py`; D — зависимости на константы (`config`) импортируются напрямую, заменять их для тестов нельзя; I — N/A (интерфейсы отсутствуют) |
| **YAGNI** | ✅ Хорошо | Мёртвого кода мало (исключение — `main.py`-заглушка и `api.sendMessage()`) |
| **PEP 8 / идиомы Python** | ⚠️ Удовл. | В целом чисто, но: `datetime.utcnow()` (deprecated в 3.12), `print()` вместо `logging`, словари вместо датаклассов, `os.path` вместо `pathlib` вперемешку с `pathlib` |
| **React-идиомы** | ⚠️ Удовл. | Прямая мутация объектов в state (см. ниже); не используются `useCallback`/`useMemo`, состояние не вынесено в reducer/context |
| **Безопасность типов (TS)** | ❌ Нет | Фронтенд на чистом JSX, без PropTypes и TypeScript; структура SSE-событий нигде не описана |

## Технический долг и «запахи кода»

1. **Мутация state в `App.jsx`** (`handleSendMessage`): `const lastMsg = messages[messages.length-1]; lastMsg.stage1 = event.data` — объект берётся из текущего state и мутируется, после чего возвращается новый массив. Работает из-за пересоздания массива, но нарушает принципы React (риски: StrictMode, мемоизация, гонки при быстром обновлении событий). Следует использовать `map`/функциональные обновления.
2. **Single-turn UI vs multi-turn backend**: форма ввода в `ChatInterface.jsx` рендерится только при `conversation.messages.length === 0` — после первого вопроса поле ввода исчезает, а с ним возможность задать уточняющий вопрос в том же диалоге. Бэкенд и хранилище при этом полностью поддерживают мультитурн. Либо это намеренное решение («single turn», см. коммит `87b4a17`), требующее фиксации, либо незакрытый дефект UX.
3. **Хардкод модели заголовков**: `google/gemini-2.5-flash` в `generate_conversation_title()` (`backend/council.py`) не вынесен в `config.py`; по ходу жизни совета модели могут исчезнуть из OpenRouter — заголовки молча деградируют до `"New Conversation"`.
4. **Повторный парсинг**: `calculate_aggregate_rankings()` игнорирует готовое поле `parsed_ranking` из `stage2_collect_rankings()` и заново гоняет regex по всему тексту рецензии.
5. **Мёртвый код**: корневой `main.py` (hello-world из шаблона `uv`); `api.sendMessage()` и не-стриминговый роут `/message` не используются фронтендом; `reasoning_details` извлекается в `openrouter.py`, но нигде не потребляется (возможно, задел под reasoning-модели o1).
6. **Пустая Pydantic-модель**: `CreateConversationRequest` с `pass` — API требует тело `{}`; запрос без тела даст 422. Минимализм ради совместимости с `fetch`-клиентом, но API-контракт неточен.
7. **SSE-парсер без буферизации** (`frontend/src/api.js`): чанки разбиваются `split('\n')` посимвольно без учёта того, что граница SSE-фрейма может попасть на границу сетевого чанка; корректность зависит от того, что `json.dumps` экранирует переносы строк (см. `03_execution_flow.md`). Хрупко.
8. **Деанонимизация regex'ом** (`Stage2.jsx`): замена `new RegExp(label, 'g')` не учитывает контекст (заменит `Response A` и внутри inline-кода), и `label` не экранируется (пока безопасно — метки генерируются кодом).
9. **Старт-скрипт для Windows отсутствует**: `start.sh` — bash; на Windows запуск вручную в двух терминалах.
10. **`stage2_results` без валидации**: `parsed_ranking` может быть пустым, если модель не соблюла формат — фронтенд корректно скрывает блок, но рейтинг «Street Cred» в таком случае занижается без индикации пропусков.

## Безопасность и надёжность

### Проблемы безопасности
| Риск | Место | Серьёзность |
|---|---|---|
| **Path traversal в `conversation_id`**: id из URL конкатенируется в путь файла (`os.path.join(DATA_DIR, f"{conversation_id}.json")`) без валидации — `../../…` может писать за пределы `data/conversations/` | `backend/storage.py` `get_conversation_path()` | Средняя (приложение локальное, но сетевое: `0.0.0.0:8001`) |
| **Нет аутентификации/авторизации** | Весь `backend/main.py` | Средняя для локального сервиса |
| **Привязка к `0.0.0.0`**: любой в LAN может дёргать API и сжигать токены OpenRouter | `uvicorn.run(host="0.0.0.0")` | Средняя |
| **Нет валидации входных данных**: пустой `content` проходит, огромные сообщения — без лимитов (риск переполнения промпта/контекста и счёта) | `backend/main.py`, `backend/council.py` | Низкая–средняя |
| **Отсутствие rate-limiting** | `backend/main.py` | Низкая (локальный сервис) |
| **Секреты**: ключ в `.env` (gitignored — хорошо); но при ошибках `print()` может вывести URL/коды ответов, деталей запроса не печатает | `backend/openrouter.py` | Низкая |
| **Prompt injection**: контент пользователя вставляется в промпты всех стадий без экранирования | `backend/council.py` | Неотъемлемый риск LLM-приложений; стоит отметить в эксплуатации |
| **CORS**: `allow_credentials=True` при фиксированном списке origins — приемлемо для dev | `backend/main.py` | Низкая |

### Проблемы надёжности
- **Неатомарные записи JSON**: прямое `open(path, 'w')` + `json.dump`; сбой питания/процесса повреждает файл диалога безвозвратно.
- **Нет файловых блокировок**: два одновременных запроса на один диалог → «read-modify-write» гонка → потерянное обновление.
- **Дубликаты сообщений при ретрае**: `add_user_message()` без идемпотентности — повторный POST (обрыв сети, двойной клик) запишет сообщение дважды.
- **Утечки фоновых задач**: `asyncio.create_task(generate_conversation_title)` не отменяется при разрыве SSE; при обрыве задачи висит до конца таймаута (30 c) с предупреждением `Task was destroyed but it is pending`.
- **Длинные ожидания**: таймаут 120 c на модель × последовательность стадий — клиент может ждать 6+ минут при медленной сети; нет прогресса по стадиям внутри самих LLM-вызовов.
- **Нет health-проверки ключа**: при невалидном `OPENROUTER_API_KEY` все 4 вызова вернут `None`, совет вернёт «All models failed» — без диагностики причины (в логе лишь `print` из `openrouter.py`).

### Оценка по шкале
- **Общая читаемость**: 7/10 — структура ясна, docstring'и хорошие.
- **Тестируемость**: 2/10 — тестов нет; функции без DI и с импортом констант на уровне модуля.
- **Безопасность**: 4/10 — типичные «прототипные» дыры (нет auth, path traversal, нет лимитов).
- **Надёжность**: 3/10 — нет блокировок, ретраев, атомарности; риск потери данных реален.
- **Расширяемость**: 5/10 — добавить модель в совет просто (правка списка в `config.py`), но менять поведение стадий — больно.
