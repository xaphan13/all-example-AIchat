## Часть I. Фундамент: из чего вообще состоит современный фронтенд

### 1.1. Что такое SPA и почему весь интернет так теперь пишет

**SPA (Single Page Application)** — веб-приложение, которое после первой загрузки страницы больше не перезагружает её. Все переходы между «экранами», обновления списков, появление новых сообщений в чате — это не запросы браузера к серверу за новыми HTML-страницами, а манипуляции с DOM (деревом элементов страницы) прямо в браузере, выполняемые JavaScript.

Как это выглядит на практике:

| Традиционный сайт (MPA) | SPA |
|---|---|
| Каждый переход — `GET /page.html`, браузер перерисовывает страницу целиком | Одна загрузка HTML, дальше JS сам обновляет нужные куски |
| Сервер рендерит HTML | Сервер отдаёт «голые» данные (обычно JSON), HTML строит клиент |
| Состояние живёт на сервере (сессии) | Состояние живёт в памяти браузера (state) |

LLM Council — классическая SPA: браузер загружает один `index.html`, а вся работа с бэкендом (список диалогов, отправка сообщения, приём событий по SSE) идёт через асинхронные HTTP-запросы без перезагрузки страницы.

### 1.2. React — библиотека для описания интерфейса

**React** — самая популярная JS-библиотека (не фреймворк!) для построения интерфейсов, создана в Facebook (Meta) в 2013 году. Её ключевая идея: **UI описывается как функция от состояния**.

Главные концепции:

1. **Компоненты.** Интерфейс собирается из переиспользуемых кусочков-функций. Компонент — это функция, которая принимает входные данные (`props`) и возвращает описание того, что должно быть на экране.

2. **JSX** — синтаксис, в котором в JavaScript-код встраивается HTML-подобная разметка:
   ```jsx
   function Hello({ name }) {           // name — это props
     return <h1>Привет, {name}!</h1>;  // JSX: HTML-подобная разметка внутри JS
   }
   ```
   Браузер JSX не понимает — его превращает в обычные вызовы JavaScript сборщик (в нашем случае Vite через плагин `@vitejs/plugin-react`). `createRoot(...).render(<App/>)` в `main.jsx` в итоге сводится к цепочке `React.createElement()` и вставке результата в DOM.

3. **Virtual DOM (виртуальный DOM).** Когда состояние меняется, React НЕ перерисовывает страницу целиком. Он пересобирает виртуальное дерево элементов в памяти, сравнивает его с предыдущим (diff) и точечно применяет изменения к реальному DOM. Именно поэтому в коде повсюду `setState` → React сам решает, что перерисовать.

4. **State и props.**
   - `props` — данные, которые родитель передаёт ребёнку; ребёнок их менять не может (они read-only).
   - `state` — внутренние данные компонента. Единственный способ их изменить — `setState`, что запускает перерисовку.
   - Поток данных односторонний: сверху вниз, от родителя к детям.

5. **Хуки (hooks)** — функции, позволяющие «подключаться» к механизмам React из функциональных компонентов:
   - `useState(initial)` → возвращает `[значение, функция-сеттер]`;
   - `useEffect(callback, deps)` → выполняет побочный эффект (загрузка данных, подписки, scroll) после рендера; повторно — когда меняются `deps`;
   - `useRef(initial)` → «ящик», значение которого переживает перерисовки и не вызывает их (в проекте — ссылка на DOM-элемент для прокрутки).

### 1.3. Vite — сборщик и dev-сервер

**Vite** (фр. «быстрый», читается «вит») — сборщик фронтенда нового поколения от Эвана Ю (автора Vue). Решает две задачи:

- **Dev-режим (`npm run dev`)**: запускает локальный сервер на порту 5173, который поставляет исходники в браузер почти без сборки. ES-модули работают нативно, поэтому изменения файла мгновенно видны на странице через **HMR (Hot Module Replacement)** — модуль подменяется без перезагрузки страницы.
- **Production-сборка (`npm run build`)**: минифицирует и оптимизирует код (бандлинг), выдаёт статику в `dist/`.

Почему Vite быстрее старых сборщиков (Webpack): он не собирает всё приложение заранее — браузер сам запрашивает нужные модули по мере необходимости.

Родственный вопрос: **Webpack vs Vite vs Rollup vs esbuild** — Vite в dev использует нативный esbuild (на Go), а в prod — Rollup. Для нас важно одно: Vite — это «обёртка», которая даёт нам dev-сервер + HMR + сборку. Конфиг проекта в `vite.config.js` минимален, потому что Vite почти не требует настройки.

### 1.4. Vue и другие: большая картина фронтенд-мира

Раз React — библиотека, а не фреймворк, стоит понимать ландшафт:

| Технология | Тип | Ключевая идея | Синтаксис шаблонов |
|---|---|---|---|
| **React** | библиотека | JSX: разметка внутри JavaScript | JSX (`return <div>...</div>`) |
| **Vue** | фреймворк (прогрессивный) | «Реактивные шаблоны»: HTML-шаблон + скрипт + стили в одном файле `.vue` | `<template>` с директивами `v-if`, `v-for`, `v-model` |
| **Angular** | фреймворк (полный) | «Батарейки в комплекте»: DI, роутинг, формы, RxJS | атрибуты `*ngIf`, `[(ngModel)]` |
| **Svelte** | компилятор | Код компилируется в императивный JS без virtual DOM | похож на Vue |

**Сравнение React и Vue** в двух строчках: React — «JavaScript с разметкой внутри», Vue — «HTML с логикой внутри». Обе решают одну задачу (реактивный UI), просто по-разному раскладывают акценты. В этом проекте выбран React — и это самый распространённый выбор в 2026 году (React ~40% рынка против ~18% у Vue).

**Что у них общего:** все эти инструменты — реактивные библиотеки поверх одних и тех же браузерных технологий: DOM, `fetch`, события. Зная React, Vue выучится за пару дней.

## Часть II. Как устроен фронтенд LLM Council

### 2.1. Общая архитектура и поток данных

```
index.html (пустая оболочка, #root)
    ↓
main.jsx  (точка входа: React монтирует <App/> в #root)
    ↓
App.jsx   (главный компонент: состояние диалогов + вся SSE-логика)
    ├── Sidebar.jsx        (список диалогов)
    └── ChatInterface.jsx  (лента сообщений + форма ввода)
          ├── Stage1.jsx   (вкладки ответов моделей)
          ├── Stage2.jsx   (рецензии + деанонимизация + агрегатный рейтинг)
          └── Stage3.jsx   (финальный ответ председателя)
```

Все коммуникации с бэкендом (порт 8001) идут через **единственный файл `api.js`** — это «толстый» HTTP-клиент: обычные `fetch` для CRUD + ручной парсер **SSE** для стриминга событий.

Всю обработку данных фронтенд держит в **одном месте — state компонента `App`**, а не в глобальном хранилище (Redux/Zustand тут не нужны — приложение маленькое). Компоненты-потомки получают данные через `props` и сообщают о действиях через колбэки.

### 2.2. Анатомия каждого файла

#### `index.html` — точка входа Vite
```html
<div id="root"></div>
<script type="module" src="/src/main.jsx"></script>
```
- Vite-приложение всегда начинается с почти пустого HTML: вся «страница» — один `<div id="root">`, в который React вставит всё приложение.
- `type="module"` — признак ES-модуля: браузер сам подтянет и выполнит `main.jsx` (и всё, что тот импортирует).

#### `src/main.jsx` — точка монтирования
```jsx
createRoot(document.getElementById('root')).render(
  <StrictMode><App /></StrictMode>,
);
```
- `createRoot().render()` — современный React 18/19 API: создаёт «корень» и рендерит в него компонент.
- `<StrictMode>` — dev-режим двойного вызова рендеров и эффектов, чтобы поймать баги (в проде никак не влияет). Отсюда двойные `useEffect` в dev-режиме — это нормально, а не баг.

#### `src/App.jsx` — мозг фронтенда

**Состояние** (4 куска):
```jsx
const [conversations, setConversations] = useState([]);   // список диалогов для сайдбара
const [currentConversationId, setCurrentConversationId] = useState(null);
const [currentConversation, setCurrentConversation] = useState(null); // открытый диалог
const [isLoading, setIsLoading] = useState(false);        // глобальный флаг загрузки
```

**Загрузка данных** — два `useEffect`:
- на монтировании (`[]`) → `loadConversations()` — список диалогов;
- при смене `currentConversationId` → `loadConversation(id)` — детали выбранного диалога.

**Ключевой метод — `handleSendMessage`** (это ядро всего UX). Здесь применена техника **optimistic UI**:
1. Пользовательское сообщение сразу добавляется в `currentConversation.messages` (UI реагирует мгновенно, не дожидаясь сети);
2. Создаётся «пустое» assistant-сообщение с `stage1/stage2/stage3: null` и `loading: {stage1: false, ...}` — каркас, который будет наполняться по мере прихода SSE-событий;
3. Вызывается `api.sendMessageStream(...)` с колбэком на каждое событие.

**Обработка SSE-событий** — большой `switch` по `eventType`. Каждое событие обновляет последнее сообщение:
```
stage1_start      → loading.stage1 = true        (показать спиннер «Running Stage 1...»)
stage1_complete   → stage1 = event.data          (вкладки с ответами моделей)
stage2_start      → loading.stage2 = true
stage2_complete   → stage2 = event.data + metadata (label_to_model, aggregate_rankings)
stage3_start      → loading.stage3 = true
stage3_complete   → stage3 = event.data
title_complete    → перезагрузка списка диалогов (заголовок появился)
complete          → перезагрузка списка + isLoading = false
error             → лог в консоль + isLoading = false
```

Обратите внимание на паттерн обновления:
```jsx
setCurrentConversation((prev) => {
  const messages = [...prev.messages];  // 1. копия массива (иммутабельность!)
  const lastMsg = messages[messages.length - 1]; // 2. мутируем КОПИЮ
  lastMsg.stage1 = event.data;          //    (в реальном React это антипаттерн,
  return { ...prev, messages };         //    но в этом проекте работает)
});
```
Строго говоря, мутация объекта `lastMsg` — нарушение иммутабельности, но так как ссылка на объект одна и та же в старом и новом массиве, а React 19 сравнивает по ссылкам — на практике работает. Это один из технических долгов проекта (см. `docs/04_code_quality.md`).

**Рендер**: `.app` → `<Sidebar>` (слева) + `<ChatInterface>` (справа). Всё — на `props` и колбэках: `onNewConversation`, `onSelectConversation`, `onSendMessage`.

#### `src/api.js` — HTTP-клиент и ручной парсер SSE

Четыре метода:
- `listConversations()` / `createConversation()` / `getConversation(id)` — обычные `fetch` с проверкой `response.ok` и `response.json()`;
- `sendMessage(conversationId, content)` — POST без стриминга (в UI не используется, но есть);
- `sendMessageStream(conversationId, content, onEvent)` — сердце приложения.

**Как работает `sendMessageStream` (SSE без библиотек):**
```jsx
const reader = response.body.getReader();   // Streams API: читаем тело ответа по кускам
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();  // асинхронный цикл чтения
  if (done) break;
  const chunk = decoder.decode(value);          // бинарный кусок → текст
  const lines = chunk.split('\n');              // SSE-формат: строки "data: ..."
  for (const line of lines) {
    if (line.startsWith('data: ')) {
      const event = JSON.parse(line.slice(6));  // отрезаем префикс, парсим JSON
      onEvent(event.type, event);
    }
  }
}
```

**Формат SSE-событий бэкенда:** каждая строка `data: {json}` содержит `type` (например `stage1_complete`) и полезные поля (`data`, `metadata`, `message`). Это «сервер → браузер»-стрим: клиент держит POST-запрос открытым, а сервер по мере готовности шлёт события.

Важный нюанс: строки могут прийти разрезанными между чанками (граница `\n` не совпадает с границей сетевого пакета) — это известная слабость данного ручного парсера; она описана в `docs/04_code_quality.md`.

#### `src/components/ChatInterface.jsx` — лента и форма

- Локальный state: `input` (текст формы) и `messagesEndRef` (`useRef` на DOM-элемент внизу ленты).
- `useEffect` с зависимостью `[conversation]` → `scrollToBottom()`: при каждом обновлении диалога (пришло событие, обновился stage) лента автоматически прокручивается вниз — это и есть тот самый классический чат-паттерн.
- **Отрисовка сообщения** — `conversation.messages.map(...)`. Для каждого сообщения:
  - `role === 'user'` → блок «You» с `ReactMarkdown` для контента;
  - иначе → блок «LLM Council», внутри которого последовательно:
    - спиннер `loading?.stage1` → затем `Stage1` с ответами;
    - спиннер `loading?.stage2` → затем `Stage2` с рецензиями;
    - спиннер `loading?.stage3` → затем `Stage3` с финальным ответом.
- **Форма ввода появляется только при пустой истории** (`conversation.messages.length === 0`) — это и есть известное ограничение single-turn: задал вопрос — ввод исчез (см. AGENTS.md, пункт 4).
- Enter — отправка, Shift+Enter — перенос строки.

#### `src/components/Sidebar.jsx` — список диалогов

Чисто презентационный компонент (без логики): принимает `conversations`, `currentConversationId` и два колбэка. Отрисовывает заголовок, кнопку «+ New Conversation» и список с подсветкой активного диалога. Никаких запросов сам не делает — всё через props от `App`.

#### `src/components/Stage1.jsx` — ответы моделей (вкладки)

- Локальный state: `activeTab` (какая вкладка открыта).
- Каждая вкладка — модель (короткое имя: `resp.model.split('/')[1]` — например, из `openai/gpt-4o` получается `gpt-4o`).
- Контент рендерится через `<ReactMarkdown>` внутри `<div className="markdown-content">` (обязательное правило стилизации — см. AGENTS.md, пункт 5).
- Если `responses` пуст → `return null` (компонент просто ничего не рисует).

#### `src/components/Stage2.jsx` — рецензии и деанонимизация

Самый интересный компонент с точки зрения бизнес-логики:

1. **Функция `deAnonymizeText(text, labelToModel)`** — чистая функция, заменяет в тексте рецензии каждое вхождение «Response X» на короткое имя модели в **жирном начертании**:
   ```jsx
   result = result.replace(new RegExp(label, 'g'), `**${modelShortName}**`);
   ```
   Это **клиентская деанонимизация**: модели на сервере видели только метки, а подстановка имён происходит в браузере, только для показа.
2. **Вкладки** рецензентов + отрендеренная рецензия (уже деанонимизированная) внутри `ReactMarkdown`.
3. **«Extracted Ranking»** — отдельный список `parsed_ranking` (массив меток `Response A/B/C`), который бэкенд вытащил из текста рецензии регэкспом; здесь он тоже превращается в человекочитаемые имена.
4. **«Aggregate Rankings (Street Cred)»** — агрегированный рейтинг от бэкенда: позиция, имя модели, средний ранг `average_rank` и число голосов `rankings_count`. Приходит в `metadata.aggregate_rankings`.

**Важная деталь:** `metadata` (label_to_model, aggregate_rankings) приходит только по SSE и **не сохраняется на сервере** — после перезагрузки страницы рецензии остаются, но деанонимизация и рейтинг исчезают. Это описано в AGENTS.md и является известным ограничением.

#### `src/components/Stage3.jsx` — финальный ответ

Простейший компонент: если `finalResponse` пуст → `null`, иначе — блок с именем председателя (`Chairman: <короткое имя>`) и его ответом через `ReactMarkdown`.

### 2.3. Стилизация: как это устроено

Проект использует **обычные CSS-файлы с классами** (никаких CSS-модулей, Tailwind или styled-components) — минимализм в духе «vibe-coded» проекта.

- `src/index.css` — глобальные стили: сброс (`* { margin: 0; box-sizing: border-box }`), базовые шрифты, переменные `:root` и, главное, класс **`.markdown-content`** — единое оформление markdown-контента (параграфы, заголовки, списки, блоки кода, цитаты).
- `src/App.css` — только каркас `.app` (flex-раскладка на весь экран).
- `components/*.css` — стили конкретных компонентов. Тема: белые карточки на сером фоне, акцентный синий `#4a90e2`, цветные рамки-маркеры стадий (Stage 3 — зелёный, агрегаты — голубой).

Паттерн наследования: `.stage` (базовый блок карточки) определён в `Stage1.css`, а `Stage2/3` переиспользуют его + переопределяют свои детали (например, `background: #f0fff0` для Stage 3). Компоненты подключены к разметке просто по классам — через `import './X.css'`.

### 2.4. Инструменты вокруг: ESLint

`eslint.config.js` — flat config (ESLint 9). Подключены:
- `@eslint/js` (recommended) — базовые правила;
- `eslint-plugin-react-hooks` (flat.recommended) — проверка хуков (правила `rules-of-hooks`, `exhaustive-deps`);
- `eslint-plugin-react-refresh` (vite-конфиг) — предупреждает, если из модуля экспортируется не только компонент (ломает HMR);
- правило `no-unused-vars` с `varsIgnorePattern: '^[A-Z_]'` — чтобы не ругаться на компоненты-переменные с заглавной буквы.

### 2.5. Полный жизненный цикл одного вопроса — как это выглядит для пользователя

```
1. Пользователь открывает приложение  → App загружает список диалогов
2. Нажимает «+ New Conversation»     → POST /api/conversations → id в состоянии
3. Вводит вопрос, Enter              → handleSendMessage():
     a) optimistic UI: вопрос сразу появляется в ленте
     b) появляется каркас сообщения совета со спиннерами
     c) fetch POST .../message/stream → открытый стрим
4. Бэкенд шлёт SSE-события            → App обновляет последнее сообщение:
     stage1_start → спиннер «Running Stage 1...»
     stage1_complete → вкладки с ответами 3 моделей
     stage2_start → спиннер «Running Stage 2...»
     stage2_complete → рецензии (деанонимизированные) + Street Cred
     stage3_start → спиннер «Running Stage 3...»
     stage3_complete → финальный ответ председателя
     title_complete → сайдбар перезагружается (появился заголовок)
     complete → спиннеры убраны, всё готово
5. Прокрутка вниз при каждом обновлении — через scrollIntoView
```

### 2.6. Карта «где что искать» (шпаргалка)

| Если нужно... | Идти сюда |

## Часть III. Глоссарий и ответы на частые вопросы

**Что такое JSX?** Синтаксис JavaScript с встроенной HTML-разметкой; превращается сборщиком в обычные вызовы `React.createElement`. Без него можно писать, но неудобно.

**Чем отличается React от Vue от Angular?** React — библиотека (JSX, только представление, остальное — на выбор), Vue — прогрессивный фреймворк (шаблоны, «всё в одном файле»), Angular — «тяжёлый» фреймворк со встроенным решением всех задач. Для маленького локального приложения React — самый простой и распространённый выбор.

**Что делает Vite?** Dev-сервер с мгновенным обновлением (HMR) + сборщик для продакшена. В `dev` почти ничего не компилируется — браузер сам грузит ES-модули; в `build` код минифицируется в `dist/`.

**Что такое SSE?** Server-Sent Events — протокол, в котором сервер по одному открытому HTTP-соединению шлёт клиенту поток строк `data: ...`. Альтернатива — WebSocket (двусторонний канал). Для одностороннего «сервер → клиент» (как здесь: события стадий совета) SSE проще и работает на обычном `fetch`.

**Что такое «оптимистичный интерфейс» (optimistic UI)?** Показ результата действия сразу, до ответа сервера, с последующим «дополнением» данными. Здесь: вопрос появляется мгновенно, а ответ совета — по частям, по мере прихода стадий.

**Почему везде `setCurrentConversation((prev) => ...)`?** Это функциональное обновление state: React гарантирует, что `prev` — актуальное значение на момент обновления. Это защита от гонок, когда несколько обновлений происходят подряд (как при череде SSE-событий).

**Почему `msg.loading?.stage1` с вопросиком?** Optional chaining: если `loading` ещё `null`/`undefined`, выражение вернёт `undefined` вместо ошибки. Пришло из пустого каркаса сообщения, где `loading` задан, но для старых сообщений из истории его может не быть.

**Что означает `split('/')[1]`?** Модели OpenRouter именуются как `vendor/model` (например, `anthropic/claude-sonnet-4`). Для короткого имени на вкладке берётся часть после слеша. Если слеша нет — используется полное имя.

## Итог

Фронтенд LLM Council — это образцово-минималистичная SPA на React 19 + Vite: один источник состояния (`App.jsx`), тонкий HTTP-клиент с ручным парсером SSE (`api.js`), пять «глупых» презентационных компонентов и классическая CSS-стилизация. Архитектура намеренно простая — без роутера, без глобального стейта, без типов — и это соответствует философии проекта «vibe-coded прототип». Все компромиссы и технические долги (мутация объектов в state, несохранение metadata, single-turn UI, хрупкий парсер SSE) собраны в `docs/04_code_quality.md` и `docs/05_optimization_roadmap.md`.
