## 1. Что такое фронтенд вообще

**Фронтенд** (от англ. *front end* — «передний край») — это та часть веб-приложения,
которая работает в браузере пользователя. В отличие от **бэкенда** (серверной части),
фронтенд отвечает за:

- визуальное отображение (вёрстка, стили, анимации);
- интерактивность (реакция на клики, ввод текста, отправка форм);
- клиентскую логику (валидация, предпросмотр, работа с API браузера — микрофон,
  камера, файлы);
- коммуникацию с сервером (HTTP-запросы, WebSocket, SSE).

### Три базовых технологии фронтенда

| Технология | Роль | Аналогия |
|---|---|---|
| **HTML** | Структура и содержимое страницы | Каркас здания |
| **CSS** | Визуальное оформление: цвета, шрифты, отступы, анимации | Отделка и фасад |
| **JavaScript** | Логика и интерактивность | Электропроводка и лифты |

Всё остальное (React, Vue, HTMX, Vite, jQuery, Angular, Svelte…) — это **инструменты
и фреймворки**, построенные поверх этих трёх технологий. Они не заменяют HTML/CSS/JS,
а предоставляют удобные абстракции для работы с ними.

## 2. Как браузер рендерит страницу: критический базис

Понимание этого процесса необходимо, чтобы осознать, почему разные фреймворки
работают именно так.

```
HTML-текст → DOM-дерево → CSSOM-дерево → Render tree → Layout → Paint → Composite
```

1. **Парсинг HTML → DOM.** Браузер читает HTML и строит **DOM** (Document Object
   Model) — древовидную структуру объектов в памяти. Каждый тег — это узел (node).
2. **Парсинг CSS → CSSOM.** Стили превращаются в **CSSOM** — дерево правил.
3. **Render tree.** DOM и CSSOM объединяются: невидимые элементы (например,
   `display: none`) исключаются.
4. **Layout (reflow).** Браузер вычисляет координаты и размеры каждого элемента.
5. **Paint.** Отрисовка пикселей: текст, цвета, границы, тени.
6. **Composite.** Слои объединяются в финальное изображение на экране.

### DOM — это живой объект

DOM можно модифицировать из JavaScript в реальном времени:

```javascript
const div = document.createElement('div');
div.textContent = 'Привет!';
document.body.appendChild(div); // элемент мгновенно появляется на странице
```

Именно манипуляция DOM — основа всей клиентской интерактивности. Разница между
фреймворками — в том, **как** они эту манипуляцию организуют.

## 3. Эволюция подходов к фронтенду

### Эпоха 1: Статичные страницы (1991–2004)

HTML генерировался на сервере (PHP, CGI, SSI). JavaScript использовался для
мигающих баннеров и простейшей валидации форм. Страница перезагружалась при каждом
действии.

### Эпоха 2: jQuery и AJAX (2005–2014)

**AJAX** (Asynchronous JavaScript and XML, хотя XML почти никто не использовал —
везде JSON) позволил обновлять части страницы без перезагрузки. **jQuery**
(2006) стал де-факто стандартом: он упростил выбор элементов, анимации и AJAX.

```javascript
// jQuery: обновить часть страницы без перезагрузки
$('#result').load('/api/data');
```

### Эпоха 3: SPA-фреймворки (2014–настоящее)

**SPA** (Single Page Application) — приложение, которое загружается один раз, а
дальше все переходы и обновления происходят в JavaScript без перезагрузки страницы.
Родились **React** (2013), **Angular** (2010), **Vue** (2014), **Svelte** (2016).

### Эпоха 4: Гибридный ренессанс (2020–настоящее)

Растущая сложность SPA-стеков (огромные `node_modules`, медленный первый рендер,
сложность отладки) вызвала обратную волну: **HTMX**, **Hotwire/Turbo** (Rails),
**Alpine.js**, **Astro** (островная архитектура). Идея: сервер снова рендерит HTML,
а JavaScript используется точечно и минимально.

> **Данный проект находится в четвёртой эпохе** — он использует HTMX и серверный
> рендеринг через Jinja2, а не React/Vue.

## 4. React: что это и зачем

**React** — библиотека от Facebook (Meta), выпущенная в 2013 году. Не фреймворк
в строгом смысле — это библиотека для построения UI-компонентов.

### Ключевые идеи

1. **Компонентная архитектура.** UI разбивается на переиспользуемые куски:

```jsx
function ChatMessage({ text, isUser }) {
  return (
    <div className={isUser ? 'userMessage' : 'assistantMessage'}>
      {text}
    </div>
  );
}
```

2. **JSX** — синтаксис, смешивающий HTML и JavaScript. Не является валидным JS —
   требует сборщика (Babel/Vite) для трансляции.

3. **Виртуальный DOM (Virtual DOM).** React хранит в памяти копию DOM. При
   изменении состояния он сравнивает новую и старую версию (reconciliation) и
   применяет только минимальный набор изменений к реальному DOM.

4. **Однонаправленный поток данных.** Данные текут сверху вниз (от родителя к
   потомку через props). Состояние (`useState`, `useReducer`) локально в компоненте.

5. **Хуки (Hooks).** Начиная с React 16.8 (2019), логика выносится в функции:
   `useState`, `useEffect`, `useMemo`, `useCallback`.

### Экосистема

- **Next.js** — фреймворк поверх React для SSR/SSG (серверный рендеринг,
  статическая генерация), роутинг, API routes.
- **React Router** — клиентский роутинг.
- **Redux / Zustand / Jotai** — управление глобальным состоянием.
- **Vite / Webpack** — сборщики (см. раздел 6).

### Когда выбирать React

- Сложный интерактивный UI с большим количеством состояний (dashboard, IDE, таблицы).
- Команды, где React-разработчиков легко найти.
- Проекты, требующие богатой экосистемы npm-пакетов.
- Изоморфные приложения (один код на сервере и клиенте).

### Минусы

- Тяжёлая экосистема: `node_modules`, конфиги, сборка.
- Первый рендер медленнее, чем серверный HTML (пока JS загрузится и выполнится).
- Большой объём JavaScript для простых страниц — оверкилл.

## 5. Vue: что это и зачем

**Vue.js** — фреймворк от Эвана Ю (ex-Google), выпущенный в 2014 году. Занимает
промежуточное положение между React и Angular: более «всеобъемлющий», чем React,
но легче, чем Angular.

### Ключевые идеи

1. **Single File Components (SFC):** шаблон, скрипт и стили в одном файле `.vue`:

```vue
<template>
  <div :class="isUser ? 'userMessage' : 'assistantMessage'">
    {{ text }}
  </div>
</template>

<script setup>
const props = defineProps(['text', 'isUser']);
</script>

<style scoped>
.userMessage { background: #000; color: #fff; }
</style>
```

2. **Реактивность на основе прокси.** В отличие от React, где нужно явно вызывать
   `setState`, Vue автоматически отслеживает изменения через `Proxy`:

```javascript
const count = ref(0);  // реактивная переменная
count.value++;          // DOM обновится автоматически
```

3. **Директивы:** `v-if`, `v-for`, `v-model`, `v-bind` — декларативные инструкции
   прямо в шаблоне.

4. **Двустороннее связывание** через `v-model` (React требует ручной обработки).

### Экосистема

- **Nuxt.js** — SSR-фреймворк для Vue (аналог Next.js для React).
- **Pinia** — управление состоянием (пришёл на смену Vuex).
- **Vue Router** — роутинг.

### Когда выбирать Vue

- Хочется «всё включено» без сборки экосистемы по кусочкам.
- Команда предпочитает шаблонный подход (HTML-подобный) вместо JSX.
- Меньший порог входа по сравнению с React.

## 6. Vite и сборщики: зачем они нужны

### Проблема

Браузер понимает только три вещи: HTML, CSS, JavaScript (ES-модули). Но
современный фронтенд-код часто написан на:

- **TypeScript** — нужен компилятор в JS;
- **JSX/TSX** — нужен Babel/SWC для трансляции;
- **SCSS/PostCSS** — нужен препроцессор;
- **`.vue` / `.svelte`** — нужен парсер фреймворка;
- **npm-пакеты** — нужны бандлер и tree-shaking;
- **Импорты `import x from 'y'`** — нужно разрешение модулей.

Всё это делает **сборщик (bundler)** — инструмент, который берёт исходный код,
применяет трансформации и выдаёт браузеру готовые HTML/CSS/JS.

### Webpack (2012–настоящее)

Долгие годы — де-факто стандарт. Мощный, но медленный и сложный в настройке.
Конфиг на сотни строк. Dev-сервер пересобирает бандл при каждом изменении.

### Vite (2020–настоящее)

Создан Эваном Ю (автором Vue). Идея: **в dev-режиме не собирать бандл вообще**.
Vite использует нативную поддержку ES-модулей в браузере — каждый модуль грузится
отдельно по `import`. Сборка (через Rollup) происходит только для production.

```
Vite dev-сервер
  ├── /src/main.ts     → транслируется «на лету»
  ├── /src/App.vue     → парсится «на лету»
  └── node_modules/... → отдаются как ES-модули через оптимизацию (esbuild)
```

**Результат:** dev-сервер стартует мгновенно (даже на больших проектах), HMR
(Hot Module Replacement) — за миллисекунды.

### Другие сборщики

| Сборщик | Особенность |
|---|---|
| **Rollup** | Фокус на оптимизированный production-бандл (library-oriented). Vite использует его для prod. |
| **esbuild** | Написан на Go, экстремально быстрый. Vite использует для транзиции. |
| **Parcel** | Zero-config, но менее гибкий. |
| **Turbopack** | От Vercel (замена Webpack), написан на Rust. Встроен в Next.js. |
| **SWC** | Компилятор от Vercel (Rust), альтернатива Babel. |

### Важно для нашего проекта

**В данном проекте нет сборщика.** Весь JavaScript — это обычные `.js`-файлы,
которые браузер грузит напрямую через `<script src="...">`. Никакого TypeScript,
никакого JSX, никаких npm-пакетов на клиенте. Единственные «внешние» скрипты —
`marked` и `DOMPurify`, подключённые через CDN.

## 7. SPA vs MPA vs SSR: три модели веб-приложений

### MPA (Multi-Page Application)

Классическая модель. Каждый клик по ссылке → сервер возвращает новую HTML-страницу
→ браузер полностью перерисовывает окно.

```
Клик → HTTP GET → сервер рендерит HTML → полная перезагрузка страницы
```

**Плюсы:** простота, SEO, работает без JS.
**Минусы:** перезагрузка на каждом действии, нет плавных переходов.

### SPA (Single Page Application)

Браузер один раз грузит пустой HTML + большой JS-бандл. Дальше JavaScript берёт
на себя роутинг и рендеринг.

```
Первый заход → грузится HTML-скелет + React-бандл
Дальше → JS перехватывает клики, делает API-запросы, рендерит DOM
```

**Плюсы:** плавные переходы, богатый интерактив, офлайн-возможности.
**Минусы:** долгий первый рендер (надо загрузить JS), плохой SEO без доп. усилий,
сложность инфраструктуры.

### SSR (Server-Side Rendering) / Гибрид

Сервер рендерит HTML на каждый запрос (как MPA), но JavaScript на клиенте
«оживляет» страницу (hydration), и дальше переходы могут быть без перезагрузки
(как SPA). Next.js (React) и Nuxt (Vue) — главные представители.

### HTMX-подход (четвёртая модель)

HTMX — это не фреймворк, а **расширение HTML**. Он добавляет HTML-атрибутам
способность делать HTTP-запросы и частично обновлять DOM — без написания JS.

```html
<!-- Клик по кнопке → AJAX-запрос → результат вставляется в #target -->
<button hx-post="/api/data" hx-target="#target" hx-swap="innerHTML">
  Загрузить
</button>
<div id="target"></div>
```

Сервер возвращает **HTML-фрагмент** (не JSON!), который вставляется в страницу.

**Плюсы:** минимум JS, серверный рендеринг, простота.
**Минусы:** ограниченная клиентская логика, не подходит для сложных state-heavy UI.

> **Данный проект использует HTMX-подход** — серверный рендеринг через Jinja2 +
> HTMX для частичных обновлений + точечный vanilla JS для стриминга Markdown.

## 8. Server-Sent Events (SSE): потоковая передача данных

SSE — технология, позволяющая серверу **отправлять данные клиенту в реальном
времени** через постоянное HTTP-соединение. В отличие от WebSocket (двунаправленный),
SSE — **однонаправленный** (сервер → клиент), что проще и надёжнее.

### Как это работает

```
Браузер:  GET /receive (Accept: text/event-stream)
          ↓ держит соединение открытым
Сервер:   event: textDelta
          data: <div hx-swap-oob="textDelta:#msg-1">Привет</div>

          event: textDelta
          data: <div hx-swap-oob="textDelta:#msg-1">, мир!</div>

          event: endStream
          data: done
          ↓ закрывает соединение
```

### Формат SSE-сообщения

```
event: <имя события>\n
data: <данные, возможно многострочные>\n
\n  ← пустая строка = конец сообщения
```

Каждое сообщение состоит из имени события (`event:`) и данных (`data:`). Данные
могут быть любым текстом — JSON, HTML, plain text.

### SSE в данном проекте

Проект использует SSE для **стриминга ответов чат-ассистента** в реальном
времени. Сервер отправляет ~12 типов событий:

| Событие | Что несёт | Как обрабатывается |
|---|---|---|
| `messageCreated` | HTML нового пустого сообщения ассистента | HTMX swap (default) |
| `textDelta` | OOB-HTML с куском Markdown-текста | Кастомный JS: накопление + рендер через `marked` |
| `toolDelta` | OOB-HTML с аргументами вызова инструмента | Кастомный JS: стриминг в `<pre>` |
| `toolCallCreated` | HTML карточки вызова инструмента | HTMX swap (default) |
| `toolOutput` | HTML с результатом инструмента | HTMX swap (default) |
| `mcpApprovalRequest` | HTML карточки запроса одобрения MCP | HTMX swap (default) |
| `textReplacement` | OOB-HTML с заменой `sandbox:/path` → URL | Кастомный JS: regex-замена в Markdown |
| `imageOutput` | HTML с изображением | HTMX swap (default) |
| `fileOutput` | HTML карточки файла | HTMX swap (default) |
| `runCompleted` | (сигнал завершения) | HTMX swap (default) |
| `networkError` | HTML с описанием ошибки | Кастомный JS: показ баннера |
| `endStream` | (сигнал закрытия) | HTMX: `sse-close` |

## 9. HTMX: возврат к гипермедиа

**HTMX** — библиотека (~14 КБ минифицированная), которая расширяет HTML
атрибутами, позволяющими делать HTTP-запросы и обновлять DOM без JavaScript.

### Ключевые атрибуты

| Атрибут | Назначение |
|---|---|
| `hx-post`, `hx-get`, `hx-put`, `hx-delete` | HTTP-метод запроса |
| `hx-target` | CSS-селектор элемента, куда вставить результат |
| `hx-swap` | Как вставить: `innerHTML`, `outerHTML`, `beforeend`, `afterbegin`, `delete`, `none` |
| `hx-trigger` | Событие-триггер: `click`, `load`, `revealed`, `change`, кастомные |
| `hx-include` | Включить данные других элементов в запрос |
| `hx-indicator` | Элемент-индикатор загрузки |
| `hx-confirm` | Диалог подтверждения перед запросом |
| `hx-vals` | Дополнительные данные в запрос (JSON) |
| `hx-swap-oob` | Out-of-band swap — обновить элемент в другом месте страницы |
| `hx-on::after-request` | JS-обработчик после запроса |
| `hx-ext` | Подключить расширение (например, `sse`) |

### HTMX + SSE

Расширение `sse.js` добавляет атрибуты для работы с SSE:

```html
<div hx-ext="sse"
     sse-connect="/chat/123/receive"
     sse-swap="textDelta,toolCallCreated,..."
     hx-on:htmx:sse-before-message="handleCustomSseEvents(event)"
     sse-close="endStream">
</div>
```

- `sse-connect` — открывает SSE-соединение;
- `sse-swap` — перечисляет события, для которых HTMX делает стандартный swap;
- `sse-close` — событие, при котором соединение закрывается;
- `hx-on:htmx:sse-before-message` — перехват событий в JS для кастомной обработки.

### Out-of-Band (OOB) Swap

Особый механизм HTMX: элемент с `hx-swap-oob` в ответе обновляет **другой**
элемент на странице, а не тот, что указан в `hx-target`. Это позволяет серверу
в одном ответе обновить несколько частей страницы.

```html
<!-- Сервер отправляет: -->
<div hx-swap-oob="textDelta:#msg-1">кусок текста</div>

<!-- HTMX находит #msg-1 и вставляет туда "кусок текста" -->
```

В данном проекте OOB используется для стриминга: каждый `textDelta` — это OOB-элемент,
нацеленный на конкретное сообщение ассистента.

## 10. Стек фронтенда в данном проекте

### Технологии

| Технология | Версия / Источник | Роль |
|---|---|---|
| **HTML5** | — | Структура страниц |
| **CSS3** (ванильный) | `static/styles.css` (1107 строк) | Все стили, без препроцессоров |
| **Vanilla JavaScript** (ES5+) | `static/stream-md.js`, `static/audio-recorder.js` | Кастомная клиентская логика |
| **Jinja2** | Python-шаблонизатор | Серверный рендеринг HTML |
| **HTMX** | `static/htmx.min.js` (vendor) | AJAX + частичные обновления DOM |
| **HTMX SSE extension** | `static/sse.js` (vendor) | Работа с SSE через HTMX |
| **marked.js** | CDN | Парсинг Markdown → HTML |
| **DOMPurify** | CDN | Санитизация HTML (защита от XSS) |
| **SVG** (inline) | — | Иконки (микрофон, загрузка изображений) |

### Архитектура: сервер-центричная

```
┌──────────────┐     HTTP/HTML        ┌──────────────┐
│              │ ←──────────────────→ │              │
│   Браузер    │     SSE (HTML)       │   FastAPI    │
│  (HTMX + JS) │ ←──────────────────→ │  (Jinja2)    │
│              │     AJAX (HTML)      │              │
└──────────────┘                     └──────────────┘
```

Ключевое: **сервер всегда возвращает HTML, а не JSON.** HTMX берёт этот HTML
и вставляет его в DOM. JSON на клиенте не парсится вообще.

### Что нетипично для современного фронтенда

- Нет `package.json`, нет `node_modules`, нет npm.
- Нет сборщика (Vite/Webpack).
- Нет TypeScript на клиенте.
- Нет фреймворка (React/Vue/Angular/Svelte).
- Нет CSS-фреймворка (Tailwind/Bootstrap) — только ванильный CSS.
- Нет клиентского роутинга — роутинг на сервере (FastAPI).
- Внешние библиотеки (marked, DOMPurify) — через CDN, а не npm.

## 11. Поток данных в чате: пошаговый разбор

Рассмотрим полный цикл отправки сообщения и получения ответа.

### Шаг 1: Пользователь вводит текст и нажимает Send

```html
<!-- index.html -->
<textarea name="userInput" id="userInput"
  hx-on:keydown="if (event.key === 'Enter' && !event.shiftKey) {
    event.preventDefault();
    this.form.querySelector('button[type=submit]').click();
  }">
</textarea>
<button hx-post="/chat/{{ conversation_id }}/send"
        hx-target="#messages"
        hx-swap="beforeend">
  Send
</button>
```

- Enter (без Shift) → клик по кнопке Send.
- HTMX перехватывает submit формы → `POST /chat/{id}/send` с `multipart/form-data`
  (текст + возможные изображения).
- `hx-on::before-request` → `disableSendButton()` (показывает анимацию загрузки).
- `hx-on::after-request` → `this.reset(); clearImagePreview()` (очистка формы).

### Шаг 2: Сервер обрабатывает POST /send

Сервер (FastAPI, `routers/chat.py`):
1. Читает `.env` и `tool.config.json` (конфигурация перечитывается на каждый запрос).
2. Рендерит через Jinja2 HTML пользовательского сообщения (`user-message.html`)
   и пустой каркас ответа ассистента (`assistant-run.html`).
3. Возвращает HTML — HTMX вставляет его в `#messages` (через `beforeend`).

Каркас ответа содержит HTMX-SSE-разметку:

```html
<div class="assistant-run" hx-ext="sse"
     sse-connect="/chat/{id}/receive"
     sse-swap="messageCreated,toolCallCreated,..."
     hx-on:htmx:sse-before-message="handleCustomSseEvents(event)"
     sse-close="endStream">
  <div class="dots"><div></div><div></div><div></div></div>
</div>
```

### Шаг 3: HTMX открывает SSE-соединение

Браузер открывает `GET /chat/{id}/receive` как `text/event-stream`. Сервер
начинает стримить события.

### Шаг 4: Стриминг текстовых дельт

Сервер отправляет `textDelta`-события. Они **не обрабатываются стандартным HTMX
swap** — их перехватывает `handleCustomSseEvents()` в `stream-md.js`:

```javascript
if (originalSSEEvent.type === 'textDelta') {
    evt.preventDefault();           // отменить стандартный HTMX swap
    processTextDelta(originalSSEEvent);  // кастомная обработка
}
```

`processTextDelta`:
1. Парсит OOB-HTML через `DOMParser`, извлекает целевой элемент и Markdown-кусок.
2. Накапливает Markdown в `WeakMap` (ключ — DOM-элемент, значение — строка).
3. Вызывает `renderMarkdown()`:
   - `marked.parse(markdown)` → сырой HTML;
   - `DOMPurify.sanitize(html)` → безопасный HTML (XSS-защита);
   - `targetElement.innerHTML = sanitized` → обновление DOM;
   - ссылки получают `target="_blank"` и `rel="noopener noreferrer"`;
   - автоскролл, если пользователь в конце списка сообщений.

### Шаг 5: Вызовы инструментов

Когда ассистент вызывает инструмент (function, code interpreter, web search…),
сервер отправляет:
- `toolCallCreated` — HTMX swap вставляет карточку `<details>` (свёрнутый аккордеон).
- `toolDelta` — JS стримит аргументы вызова в `<pre>` внутри карточки.
- `toolOutput` — HTMX swap вставляет результат (виджет погоды, изображение, JSON…).

### Шаг 6: MCP Approval (если требуется)

Если MCP-сервер требует одобрения, сервер отправляет `mcpApprovalRequest` —
HTMX swap вставляет карточку с кнопками Approve / Reject. Форма отправляет
`POST /chat/{id}/approve` через HTMX, после чего стрим возобновляется.

### Шаг 7: Завершение

Сервер отправляет `endStream` → HTMX видит `sse-close="endStream"` → закрывает
SSE-соединение → срабатывает `hx-on::sse-close="reEnableSendButton()"` →
кнопка Send снова активна.

| `audio-recorder.js` | **КАСТОМ:** MediaRecorder → FormData → POST /audio/transcribe | 129 строк |

### Кастомный JavaScript: детальный разбор

#### `stream-md.js` — ядро стриминга

**Глобальное состояние:**
```javascript
window._streamingMarkdown = new WeakMap();  // DOM-элемент → накопленный Markdown
```

`WeakMap` используется намеренно: когда элемент сообщения удаляется из DOM,
сборщик мусора автоматически очищает и связанный Markdown — нет утечек памяти.

**Основные функции:**

| Функция | Что делает |
|---|---|
| `handleCustomSseEvents(evt)` | Диспатчер SSE-событий. Перехватывает `textDelta`, `toolDelta`, `textReplacement`, `networkError`, `endStream`. Остальные события идут в стандартный HTMX swap. |
| `processTextDelta(sseEvent)` | Парсит OOB-HTML, достаёт Markdown-кусок, накапливает в WeakMap, рендерит через `marked` + `DOMPurify`. |
| `processToolDelta(sseEvent)` | Парсит OOB-HTML, стримит аргументы вызова инструмента в `<pre>`. Поддерживает режимы `stream` (накопление) и `replace` (полная замена). |
| `processTextReplacement(sseEvent)` | Заменяет `sandbox:/path/to/file` на реальный URL скачивания в накопленном Markdown. Использует regex по текущему Markdown-состоянию. |
| `parseOobSwap(oobHTML, eventType)` | Универсальный парсер OOB-элементов: извлекает `hx-swap-oob`-атрибут, целевой селектор и контент. |
| `renderMarkdown(targetElement, markdown, fallback)` | Рендеринг: `marked.parse()` → `DOMPurify.sanitize()` → `innerHTML`. Постобработка ссылок (`target="_blank"`). Автоскролл. |
| `disableSendButton()` / `reEnableSendButton()` | Управление состоянием кнопки Send (текст ↔ анимация загрузки). |
| `showNetworkError(detail)` / `removeNetworkError()` | Показ/скрытие баннера сетевой ошибки. |
| `openImagePreview(src)` / `closeImagePreview()` | Полноэкранный просмотр изображений (overlay создаётся on-demand). |
| `previewImages(input)` / `clearImagePreview()` | Превью выбранных для отправки изображений (FileReader → data URL). |

#### `audio-recorder.js` — запись и транскрибация

IIFE-модуль (Immediately Invoked Function Expression), ничего не утекает в
глобальную область видимости.

| Компонент | Что делает |
|---|---|
| `startRecording()` | Запрашивает микрофон через `navigator.mediaDevices.getUserMedia`, создаёт `MediaRecorder`, собирает chunks. |
| `stopRecording()` | Останавливает запись, освобождает микрофер (`stream.getTracks().forEach(t => t.stop())`). |
| `transcribe(blob)` | `FormData` с аудио → `POST /audio/transcribe` → текст вставляется в textarea ввода. |
| Клик по `#micButton` | Toggle: если запись идёт — стоп, иначе — старт. |

SVG-иконки микрофона и стоп встроены прямо в JS как строки — нет внешних
зависимостей для иконок.

## 13. Сравнение: почему не React/Vue в этом проекте

### Критерии выбора

| Критерий | React/Vue + Vite | HTMX + Jinja2 (этот проект) |
|---|---|---|
| **Тип приложения** | Богатый интерактивный UI (dashboard, IDE) | Чат + форма настроек |
| **Сложность состояния** | Много состояний на клиенте | Минимальное: стриминг текста + формы |
| **Размер JS-бандла** | 100–500 КБ+ | ~20 КБ (HTMX + SSE + кастомный JS) |
| **Первый рендер** | Медленный (надо загрузить и выполнить JS) | Мгновенный (серверный HTML) |
| **Инфраструктура** | node_modules, package.json, сборщик, конфиги | Ничего лишнего — только .js-файлы |
| **SEO** | Требует SSR (Next.js/Nuxt) | Из коробки (серверный HTML) |
| **Команда** | Нужны frontend-разработчики | Достаточно Python-разработчика |
| **Обновление UI** | JSON → Virtual DOM → diff → real DOM | HTML-фрагмент → прямой DOM swap |
| **Стриминг** | WebSocket или SSE + клиентский парсинг JSON | SSE + HTML-фрагменты (HTMX swap) |

### Почему HTMX подходит для этого проекта

1. **Чат — это по сути поток текста.** Нет сложной клиентской логики: текст
   накапливается и рендерится. `WeakMap` + `marked` — этого достаточно.
2. **Сервер уже рендерит HTML через Jinja2.** HTMX позволяет переиспользовать
   шаблоны и для AJAX-ответов, и для SSE — один и тот же `assistant-step.html`
   работает и при первоначальной загрузке, и при стриминге.
3. **Минимум JavaScript = минимум ошибок.** Весь кастомный JS — ~470 строк.
   Для сравнения: типичный React-чат потребовал бы 2000–5000 строк + зависимости.
4. **FastAPI + Jinja2 — естественная связка.** Python-разработчику не нужно
   изучать npm-экосистему.
5. **SSE идеально ложится на HTMX.** Расширение `sse.js` + атрибуты — и стриминг
   работает без единой строки клиентского кода (для простых случаев).

### Когда этот проект пришлось бы переписывать на React/Vue

- Если появится сложный редактор сообщений (WYSIWYG, drag-and-drop).
- Если потребуется офлайн-режим (PWA, IndexedDB).
- Если UI станет state-heavy: дашборд с десятками виджетов, фильтры, сортировки.
- Если появится клиентский роутинг с глубокими вложенными состояниями.
- Если команда вырастет и появится фронтенд-специалист.

## 14. Словарь терминов

| Термин | Определение |
|---|---|
| **DOM** | Document Object Model — древовидное представление HTML в памяти браузера. Можно менять из JS. |
| **CSSOM** | CSS Object Model — дерево CSS-правил, объединяется с DOM в render tree. |
| **Virtual DOM** | Копия DOM в памяти (React). Сравнение (reconciliation) → минимальные изменения реального DOM. |
| **SPA** | Single Page Application — приложение в одном HTML, переходы через JS без перезагрузки. |
| **MPA** | Multi-Page Application — классические перезагрузки страниц. |
| **SSR** | Server-Side Rendering — сервер рендерит HTML, клиент «оживляет» (hydration). |
| **CSR** | Client-Side Rendering — рендеринг в браузере через JS (React без SSR). |
| **SSE** | Server-Sent Events — однонаправленный стриминг от сервера к браузеру через HTTP. |
| **WebSocket** | Двунаправленный протокол поверх TCP, для real-time (чаты, игры). |
| **AJAX** | Asynchronous JavaScript and XML — запросы без перезагрузки (сейчас JSON вместо XML). |
| **HMR** | Hot Module Replacement — замена модулей в браузере без перезагрузки (Vite, Webpack). |
| **Bundler** | Инструмент сборки: объединяет модули, трансформирует (TS→JS, JSX→JS), минифицирует. |
| **Tree-shaking** | Удаление неиспользуемого кода из бандла (dead code elimination). |
| **Polyfill** | Код, реализующий возможность, которую браузер не поддерживает нативно. |
| **CDN** | Content Delivery Network — распределённая сеть серверов для отдачи статики. |
| **XSS** | Cross-Site Scripting — внедрение вредоносного JS через пользовательский ввод. Защита: санитизация (DOMPurify). |
| **OOB Swap** | Out-of-Band Swap — HTMX-механизм обновления элемента вне основного `hx-target`. |
| **Hydration** | «Оживление» серверного HTML клиентским JS (React SSR, Next.js). |
| **Jinja2** | Python-шаблонизатор: `{% %}` для логики, `{{ }}` для вывода, наследование через `{% extends %}`. |
| **WeakMap** | JS-структура: Map, где ключи — объекты, и при удалении объекта-ключа запись автоматически очищается (нет утечек памяти). |
| **MediaRecorder API** | Браузерный API для записи аудио/видео из микрофона/камеры. |
| **DOMParser** | Браузерный API для парсинга HTML-строки в DOM-документ без вставки в страницу. |
| **IIFE** | Immediately Invoked Function Expression — функция, выполняющаяся сразу при определении. Изолирует область видимости. |
