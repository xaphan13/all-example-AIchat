# Агрегаторы моделей: надёжность, стоимость и безопасность (Часть 3)

> Дата: 21.09.2026
> Источники: код 6 проектов репозитория + документация OpenRouter/LiteLLM/OpenAI SDK.
> Часть 3 из 3. Часть 1 — инвентаризация, Часть 2 — библиотеки и примеры кода.

Разница между «работает на моём ноутбуке» и «работает в продакшене» при работе с
внешней моделью — это четыре вещи: **таймауты, повторы, деградация и учёт расходов**.
Плюс пятая, если речь об агрегаторе: **согласованность поведения разных провайдеров
за одним именем модели**. Разберём каждую на коде репозитория и на том, как надо.

---

## 1. Таймауты

Таймаут — первое, что забывают. Дефолт OpenAI SDK — **10 минут**, дефолт `httpx` — 5 с
на все фазы. Ни то, ни другое не годится для интерактивного чата.

Состояние в репозитории:

| Проект | Таймаут | Комментарий |
|---|---|---|
| AI-Chatbot | не задан | дефолт SDK (10 мин) |
| GroqStreamChain | не задан | — |
| llm-council-karpathy | `120.0` c (дефолт функции), заголовок — `30.0` | единственный с осознанным таймаутом |
| openai-responses | не задан | дефолт SDK |
| Quorum | не задан | дефолт LangChain/OpenAI |
| rag-knowledge-base-chatbot | `llm_timeout_seconds = 60` | вынесен в конфиг |

Правильная практика — таймаут **дифференцированный**: отдельно на подключение,
отдельно на чтение, отдельно на весь запрос (для стрима — на паузу между чанками):

```python
client = AsyncOpenAI(
    api_key=..., base_url="https://openrouter.ai/api/v1",
    timeout=httpx.Timeout(60.0, connect=5.0, read=30.0, write=10.0),
)
```

Для длинных генераций общий таймаут должен покрывать полный ответ; для стрима —
защищать от «зависшего» соединения, а не от долгой генерации.

## 2. Повторы и backoff на 429/5xx

Что делает OpenAI SDK автоматически (и о чём часто не знают):

- **2 повтора** по умолчанию с коротким экспоненциальным backoff;
- повторяются: ошибки соединения, **408**, **409**, **429**, **>= 500**;
- **не повторяется** уже начатое потребление стрима (чтобы не дублировать вывод);
- таймаут-запросы ретраятся дважды; настройка — `max_retries`, в том числе
  через `client.with_options(max_retries=5)`.

Другими словами: проекты на `openai.AsyncOpenAI` (AI-Chatbot, openai-responses,
RAG-чатбот) **де-факто уже имеют ретраи**, даже если автор об этом не думал. А вот
проекты на ручном `httpx` и на `ChatOpenAI` — нет:

| Проект | Retry | Backoff | Обработка 429 |
|---|---|---|---|
| AI-Chatbot | неявно 2× (SDK) | экспоненциальный (SDK) | через SDK |
| GroqStreamChain | нет | — | ошибка глотается и заменяется заглушкой |
| llm-council-karpathy | **нет** | — | `raise_for_status` → модель молча выпадает из совета |
| openai-responses | неявно 2× (SDK) | экспоненциальный (SDK) | через SDK |
| Quorum | нет | — | ошибка уходит текстом в стрим |
| rag-knowledge-base-chatbot | да, в `normalizer.py` | **линейный** `backoff_ms * attempt` | плюс fallback-модель |

Единственная ручная реализация повторов — в RAG-чатботе
(`app/services/normalizer.py`), и это линейный backoff:

```python
for attempt in range(1, max_attempts + 1):
    ...
    await asyncio.sleep((retry_backoff_ms * attempt) / 1000.0)
```

Линейный backoff без джиттера — риск «стада» одновременных повторов при массовых 429.
Правильнее — экспоненциальный с джиттером; в LiteLLM это `num_retries`, в tenacity —
`wait_exponential_jitter`.

Отдельная ловушка: **свой таймаут + свои повторы = дублирование**. Если вы ставите
`max_retries=3` в SDK и ещё оборачиваете вызов в свой цикл повторов, реальное число
попыток перемножается, а таймауты складываются. Ретраи должны жить на одном уровне.

## 3. Деградация: fallback

Три разных механизма, которые часто путают:

1. **Fallback на уровне провайдера** — за одним именем модели агрегатор сам выбирает
   резервного провайдера. У OpenRouter это `allow_fallbacks` (по умолчанию `true`).
2. **Fallback на уровне модели** — упала модель, берём другую. У OpenRouter — массив
   `models: [...]`; у LiteLLM Router — `fallbacks=[{...}]`; у Quorum/RAG — своя логика.
3. **Graceful degradation** — не заменять, а просто исключить отказавший элемент.
   Так устроен совет моделей в `llm-council-karpathy`: упавшая модель пропускается,
   совет продолжает работу (`if response is not None`).

Реализовано в репозитории только третье (llm-council) и частично второе (RAG-чатбот,
`models_to_try = [model, get_llm_fallback_model()]`).

Как надо — пример с двумя уровнями сразу:

```python
response = await client.chat.completions.create(
    model="anthropic/claude-sonnet-4.5",
    messages=messages,
    extra_body={
        "models": ["anthropic/claude-sonnet-4.5", "openai/gpt-5-mini"],  # уровень модели
        "provider": {"allow_fallbacks": True, "require_parameters": True},  # уровень провайдера
    },
)
```

Здесь `models` — мягкая цепочка «попробуй следующую модель», `allow_fallbacks` —
«внутри каждой модели найди живого провайдера», `require_parameters` — «не соглашайся
на провайдера, который не умеет нужные тебе параметры». Третий пункт — самое коварное:
без него structured output или tool calling может тихо деградировать.

## 4. Согласованность за одним именем модели

Специфика агрегаторов: **одно имя модели — разные провайдеры за ним**. Это даёт
сюрпризы, которых нет при прямом обращении к вендору:

- **Смена формата параметров.** Часть моделей требует `max_tokens`, часть —
  `max_completion_tokens`. RAG-чатбот решает это функцией `_token_param()`, подставляя
  `max_completion_tokens` для `o1*`/`gpt-5*`; Pydantic AI — флагом
  `openai_chat_supports_max_completion_tokens=False` для OpenRouter.
- **Разное поведение стрима.** У OpenRouter usage приходит **ровно один раз** в
  последнем чанке перед `[DONE]`, и этот чанк содержит непустой массив `choices`
  (в отличие от спецификации OpenAI). Код, который просто берёт последний чанк как
  «дельту», может ошибиться.
- **Разные наборы параметров.** Отсюда `require_parameters` — единственный способ
  гарантировать, что выбранный провайдер умеет то, что вы просите.
- **Разные политики данных.** Отсюда `data_collection: "deny"` и `zdr: true`, если это
  требование компании.

Практический вывод: при работе через агрегатор **обязательно явно фиксировать
требуемые параметры** и проверять поведение на конкретных выбранных провайдерах, а не
полагаться на то, что «OpenAI-совместимо значит одинаково».

## 5. Учёт токенов и стоимости

Есть лишь в двух проектах из шести.

**Quorum** — через колбэк LangChain (`TokenTrackingCallback`, подключается в
конструктор `ChatOpenAI` через `callbacks=callbacks`). Разбирает usage в трёх форматах
(OpenAI `token_usage`, Anthropic `usage`, Google `usage_metadata`) и считает стоимость
по таблице `MODEL_PRICING_CONFIG` (цены из документации OpenRouter). Хранение —
**in-memory** (`TokenTrackingManager`, под `asyncio.Lock`), то есть **теряется при
рестарте**. Важный нюанс: в стриме usage обычно недоступен, и код это глушит —
потоковые ответы агентов в стоимость попадают не всегда.

**RAG-чатбот** — из `response.usage` берутся `prompt_tokens`/`completion_tokens` и
уходят в метрики Prometheus (`llm_requests_total`, `llm_tokens_total`, `llm_cost_usd`)
через `estimate_cost(model, inp, out)`, плюс в ContextVar для трассировки и в
debug-лог. Аккумулятор — в пределах запроса.

Практика, которой не хватает:

```python
response = await client.chat.completions.create(...)
usage = response.usage                       # prompt_tokens, completion_tokens
cost = usage.prompt_tokens / 1e6 * PRICES[model]["in"] \
     + usage.completion_tokens / 1e6 * PRICES[model]["out"]
```

Для агрегатора есть ещё один точный источник: **эндпоинт статистики генерации**
OpenRouter — `GET /api/v1/generation?id=$GENERATION_ID`, возвращающий фактические
данные по конкретной генерации (включая стоимость). Это надёжнее, чем локальный
пересчёт по прайсу, особенно когда за одним именем модели стоят разные провайдеры с
разными ценами.

Для стрима usage нужно **явно запрашивать** (у части агрегаторов — отдельным полем
тела запроса), иначе его просто не будет в чанках.

## 6. Безопасность ключей

Ключ агрегатора — это ключ **ко всем моделям сразу**, поэтому его утечка дороже, чем
утечка ключа одного вендора. Правила и состояние в репозитории:

**Что хорошо:**
- Ключи читаются из окружения/БД, а не хардкодятся: `llm-council` и Quorum —
  из env (dotenv), RAG-чатбот — БД `app_config` → env, Quorum — БД настроек → env.
- В Quorum ключ **маскируется** при выдаче наружу (`_mask_api_key`), а в логировании
  есть фильтр чувствительных ключей (`api_key`, `token`, `password`, `secret`,
  `authorization` → `***`).
- Ключ никогда не передаётся на фронтенд — все вызовы идут из бэкенда.

**Что плохо:**
- **Захардкоженный рабочий ключ в репозитории** —
  `../rag-knowledge-base-chatbot/scripts/test_yescale_api.py`: ключ агрегатора YesScale
  стоит дефолтом env-переменной прямо в коде. Такой ключ нужно считать
  скомпрометированным и отозвать; в коде должен быть явный отказ при отсутствии env.

  ```python
  # Так нельзя:
  API_KEY = os.getenv("YESCALE_API_KEY", "sk-AQsh...")   # ключ в репозитории

  # Так надо:
  API_KEY = os.environ["YESCALE_API_KEY"]                 # падаем, если не задан
  ```

- Ключ не валидируется на `None` (`llm-council`: `os.getenv("OPENROUTER_API_KEY")` без
  проверки) — вместо внятной ошибки конфигурации получится `Bearer None` и 401.

**Практика для продакшена:**

1. Ключ — из секрет-менеджера (Vault, AWS Secrets Manager, Doppler) или минимум из
   `.env` вне репозитория; `.env` — в `../.gitignore`.
2. **Отдельный ключ на каждый сервис** и лимит расходов на ключ (OpenRouter это
   позволяет) — тогда утечка ограничена бюджетом.
3. Маскирование секретов в логах и трассировке; тела запросов к LLM в debug-логах
   усекать (как в RAG-чатботе — до 4000 символов).
4. Ротация по расписанию и обязательная ротация при утечке/подозрении.
5. Pre-commit-сканер секретов (`gitleaks`, `detect-secrets`) — дешёвая страховка
   именно от случая YesScale.

## 7. Наблюдаемость

Что видно в репозитории: RAG-чатбот — эталон (Prometheus-метрики по запросам, токенам
и стоимости, OpenTelemetry-трассировка, structlog с `llm_call_log_var`); Quorum —
structlog плюс трекинг токенов, но в памяти; остальные — почти ничего
(`llm-council` печатает ошибку `print`-ом).

Минимум для агрегатора, который стоит логировать **на каждый вызов**: имя модели,
выбранный провайдер (если агрегатор его вернул), длительность, `finish_reason`,
токены, стоимость, признак повтора. Отдельно — счётчики 429 по модели и по провайдеру:
именно они показывают, что агрегатор деградирует, а не что «модель стала тупая».

## 8. Тестирование

Ни один проект не имеет тестов именно на слой доступа к провайдеру. Что стоит делать:

1. **Контрактный тест на агностичность.** Один и тот же сценарий против двух
   провайдеров агрегатора — проверяет, что вы не завязались на специфику одного.
2. **Тест на параметры.** Что ваш `_token_param`/профиль выдаёт корректный набор
   параметров для «сложных» моделей (`o1*`, `gpt-5*`).
3. **Тест на error-path.** Подмена транспорта (в OpenAI SDK — свой `http_client`,
   в `httpx` — `MockTransport`) и проверка, что 429 приводит к повторам, 5xx — к
   fallback, а не к «молчаливому None» (как сейчас в `llm-council`).
4. **Тест на стрим.** Что usage из финального чанка OpenRouter разбирается правильно и
   что обрыв стрима не приводит к бесконечному повисшему соединению.
5. **Golden-тест стоимости.** Фиксированный usage → ожидаемая стоимость; ловит
   расхождение прайса с реальностью.

## 9. Чек-лист для проекта, подключающего агрегатор

- [ ] Ключ из окружения/секрет-менеджера, с проверкой на пустое значение
- [ ] `base_url` агрегатора в конфиге, а не литералом в коде
- [ ] Заголовки атрибуции `HTTP-Referer` и `X-OpenRouter-Title` (или `OR_SITE_URL`/
      `OR_APP_NAME` для LiteLLM)
- [ ] Явные `timeout` (дифференцированные) и `max_retries` — ровно на одном уровне
- [ ] Настроена деградация: `providers.allow_fallbacks` + цепочка `models`
- [ ] `require_parameters: true`, если нужны tool calling / structured output
- [ ] Политика данных зафиксирована: `data_collection`, `zdr` — если требуется
- [ ] Учёт токенов и стоимости (Prometheus-метрики или эндпоинт статистики генерации)
- [ ] Маскирование ключей в логах, усечение тел запросов
- [ ] Pre-commit-сканер секретов
- [ ] Контрактный тест на двух провайдерах агрегатора + тест error-path
- [ ] Один HTTP-клиент на процесс (переиспользование соединений), а не новый на вызов

## 10. Итог цикла

- **Проекты-агрегаторы (2 из 6)** используют два разных подхода: ручной `httpx`
  (llm-council) и LangChain `ChatOpenAI` (Quorum). Оба обходят стороной специфичные
  для агрегатора возможности — заголовки атрибуции, `provider`-роутинг, `models`-fallback.
- **Официальный SDK OpenRouter (`pip install openrouter`) в репозитории не используется**
  вообще, хотя документация вендора рекомендует именно его.
- **LiteLLM, Portkey и прочие шлюзы не применяются** — при том, что LiteLLM Router даёт
  из коробки то, чего в проектах нет: fallback, retry и единый интерфейс к 100+ провайдерам.
- **Надёжность — самое слабое место репозитория:** таймауты почти не заданы, ручных
  повторов почти нет, обработка 429/5xx систематически отсутствует. Частично это
  компенсирует OpenAI SDK с его дефолтными двумя повторами — но только в проектах,
  которые его используют напрямую.
- **Лучшая архитектура для агрегаторов уже есть в репозитории** — `LLMGateway` в
  RAG-чатботе с `base_url` из БД: смена агрегатора там — операция конфигурации, а не
  правка кода. Остальным проектам стоит смотреть именно на этот паттерн.
